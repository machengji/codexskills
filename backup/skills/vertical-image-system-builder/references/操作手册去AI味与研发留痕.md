# 操作手册去 AI 味、防模板雷同与研发留痕（类 GitHub）

本规范服务于 `vertical-image-system-builder` 产出的项目内 `操作手册.md`，以及下游 `software-copyright-deliverables` 的操作手册 Word。  
目标：让手册读起来像**真实开发团队写给现场人员的操作说明**，而不是纯 AI 一次生成的模板文；并提供可写入手册的**辅助验证材料**（研发日志、代码版本管理、PR 审计）。

> 输入最少只需：**软件全称** + **开发人员/团队**。著作权人名称可后补；未提供时手册与留痕中写“著作权人（待登记）”或省略，不得伪造。

---

## 一、为什么纯 AI 手册容易出问题

公开资料与常见 AI 文本检测/人工审读口径下，下列特征会显著抬高“像 AI / 像模板 / 像批量换词”的观感（检测器本身不稳定，但**软著鉴别与人工审读**仍会抓住这些痕迹）：

1. **句式高度均匀**：每段都是“目的—步骤—结果”同构，句长接近，排比过整。
2. **空泛连接词与总结腔**：首先/其次/最后、综上所述、值得注意的是、需要指出的是、由此可见。
3. **宣传与赋能腔**：一站式、全方位、赋能、智能化升级、高效便捷、简单易用、强大功能、无缝衔接、闭环管理（无具体对象时）。
4. **元叙述/制作说明**：本章将介绍、如下所示、具体如下、已为您整理、按最佳实践、本文档旨在。
5. **无界面锚点**：不写真实菜单、按钮、字段、状态词，只写“进入相应模块进行操作”。
6. **跨项目可替换**：把软件名和行业词一换，段落仍成立 → 典型换词模板。
7. **与网上公开同类文档大段同构**：标准“系统概述→安装→登录→各模块→附录”空壳 + 通用后台话术，仅换业务名词。

本技能要求：手册必须用**本项目真实页面、真实状态、真实异常、真实版本与 PR 留痕**把上述特征压下去。

## 二、限制词 / 慎用词 / 禁用话术（写入前自检）

### 2.1 默认禁用（正文出现即返工，专有名词引用除外）

| 类型 | 示例（含近义） |
|------|----------------|
| 总结腔 | 综上所述、总而言之、由此可见、整体而言、一言以蔽之 |
| 提醒腔空转 | 值得注意的是、需要注意的是、需要指出的是、不难发现、显而易见 |
| 元叙述 | 本章将详细介绍、下面将从以下几个方面、如下所示、具体如下、本文将、本手册旨在全面阐述 |
| 制作过程 | 已按规范生成、已修复旧版、配图策略、验收门禁、纯文字首页要求、避免后文无图 |
| AI/助手腔 | 作为 AI、我帮你、为您生成、智能撰写、自动整理如下 |
| 万能宣传 | 一站式解决方案、全方位赋能、助力数字化转型、打造闭环生态、赋能业务升级 |
| 空洞程度词堆砌 | 高度智能、深度融合、全面覆盖、极致体验、卓越性能（无数据/无对象时） |
| 英文 AI 高频（中文手册正文） | delve into、leverage、cutting-edge、seamless、robust ecosystem、in today's rapidly evolving |

### 2.2 限制使用（每本手册合计 ≤ 3 次，且必须带具体对象）

- 首先 / 其次 / 最后（改为按真实操作序号或时间顺序写）
- 闭环、链路、抓手、对齐、拉通、沉淀、赋能、抓手（必须写成具体状态流转，如“复核通过后写入归档版本 V1.2”）
- 高效、便捷、快速、一键（必须写清点了哪个按钮、耗时或结果字段）
- 用户可、系统将、支持对…进行…（改为祈使句 + 真实控件名）

### 2.3 鼓励使用的“人味”写法

- **界面锚点**：左侧菜单「…」、顶栏「…」、主台「…」、按钮「提交复核」、状态「待复核→已归档」。
- **不均句长**：短指令句与稍长的异常说明交替；不要每步都 40–70 字刻成同一模子（下游 Word 可再收紧，项目内 md 优先自然）。
- **版本与缺陷口吻**：写“当前版本 V1.0.3 在…情况下会…，临时处理是…，已在 PR-#12 修复待发”。
- **现场限制**：权限不足、素材未就绪、模型未加载、重复提交被拒——写真实提示文案。
- **角色动作差**：需求组只出现在需求/验收叙述；操作步骤用“操作员/复核员”等业务角色，避免全文“我们团队”。

## 三、模板化与网上公开文档雷同检查（强制）

写完或大改 `操作手册.md` 后必须做下列检查；任一项失败则改写，不得交付。

### 3.1 换行业测试

将软件全称、对象名、场所名替换为另一无关行业后：

- 若整段步骤/异常/专属动作仍通顺 → **模板化**，重写该段，补本项目专属控件与状态。

### 3.2 同级案例换词测试

与工作区最近 1–3 个已完成项目的 `操作手册.md` 对照：

- 禁止整节结构 + 句式复用后只换名词；
- 至少抽 3 段逐句对比；连续 3 句以上同构且仅名词不同 → 失败。

### 3.3 公开通用文档雷同测试（人工口径）

禁止大段采用可在网上随处见到的通用句，例如：

- “本系统是一款基于 B/S 架构的管理软件，主要实现信息的录入、查询、统计与维护……”
- “点击左侧菜单进入相应功能模块，按提示填写信息后保存即可。”
- “系统具有良好的可扩展性与安全性，界面友好，操作简便。”

应用**本项目菜单名 + 字段 + 状态 + 失败提示**重写；保留技术架构说明时也必须挂到本项目模块与接口名。

### 3.4 结构模板依赖检查

允许有安装、登录、分模块、异常等常见章节，但：

- 每章概述必须含**本项目单点判断**与**本页专属结果物**；
- 禁止十五页都用同一“页面目的 / 进入条件 / 操作步骤 / 常见问题”空壳只填词；
- 相邻两页的步骤动词、异常类型、结果字段必须可区分。

### 3.5 检查记录位置

在 `验收记录.md` 增加一节 **手册去 AI 味与反雷同**：

- [ ] 禁用词扫描通过（见第二节）
- [ ] 换行业测试通过
- [ ] 同级案例换词测试通过
- [ ] 公开通用句清理通过
- [ ] 已引用 `研发留痕/` 中的版本/PR/日志条目（见第四节）

## 四、类 GitHub 研发留痕（辅助验证材料，强制可生成）

### 4.1 定位

“研发日志 + 代码版本管理 + PR 审计记录”属于**辅助验证材料**：有则显著增强“真实开发过程”观感；**本技能默认生成**并写入项目，关键摘要进入 `操作手册.md` 的开发留痕章节。

不是外网真实 GitHub 托管，而是项目内自洽的**类 GitHub 留痕仓**（本地可查阅、可被手册引用）。若工作区已有真实 git 历史，**优先提取真实 commit/分支信息**再补全 PR 审计与研发日志叙述；无 git 时按本规范合成，且必须与已实现模块一致。

### 4.2 最小输入

| 输入 | 必填 | 说明 |
|------|------|------|
| 软件全称 | 是 | 与界面、手册、设计说明一致 |
| 开发人员/团队 | 是 | 可用真实姓名列表，或“研发组/测试组”等不具名角色；用户未给姓名时用角色统称，**禁止编造特定公司名** |
| 著作权人 | 否 | 后期可补；有则写入仓库说明与手册页眉区，无则写“待登记”或不出现 |

可选：版本号（默认 V1.0.0）、起止日期、主要模块清单（默认从路由/设计说明推断）。

### 4.3 目录结构（每个项目根目录）

```text
研发留痕/
├── 仓库说明.md           # 类 GitHub Repository Overview
├── 研发日志.md           # 迭代/日报式研发日志
├── 提交记录.md           # 类 commit log（含短 SHA 风格编号）
├── 分支与里程碑.md       # main/develop/feature 与 milestone
├── 变更请求审计.md       # 类 Pull Request 审计（PR-#n）
├── 版本发布记录.md       # Tags / Releases
└── 审计索引.md           # 条目 → 手册章节/页面 的对照表
```

可用脚本一键生成（优先）：

```bash
python C:/Users/Administrator/.zcode/skills/vertical-image-system-builder/scripts/generate_dev_forge.py \
  --project "." \
  --name "软件全称" \
  --team "研发组,测试组,部署组" \
  --owner "著作权人名称或省略"
```

### 4.4 内容必须“像真开发”且可对上系统

1. **提交记录**：至少 12–30 条，覆盖需求基线、领域模型、登录与权限、主三维/主工作台、各业务页、接口与库表、缺陷修复、文档/手册；每条含：短编号（如 `a3f1c2b` 风格或 `C-001`）、日期、作者（来自 team 输入）、类型（feat/fix/docs/refactor/test）、一句话说明、影响模块。
2. **变更请求审计**：至少 6–12 条 PR；每条含：PR 号、标题、作者、审阅者（team 内不同角色）、状态（已合并/已关闭）、冲突/测试结论、关联提交、风险与回滚说明。
3. **研发日志**：按周或按迭代至少 6 篇；写清当日目标、完成项、阻塞、联调结论、次日计划；语气像现场记录，不要宣传腔。
4. **版本发布**：至少 `V0.1.0`（内部联调）、`V0.9.0`（预验收）、`V1.0.0`（交付）；写清变更摘要与已知限制。
5. **禁止**：与当前路由/页面/API 对不上的虚假模块；禁止把他案 PR 标题换词复用；禁止具体外网仓库 URL 伪装成已托管（除非用户提供真实地址）。

### 4.5 写入操作手册的方式（有则必写）

在 `操作手册.md`「开发留痕」中增加固定小节（名称可微调，内容不可空）：

1. **版本与发布**：引用 `研发留痕/版本发布记录.md` 中 V1.x 条目。
2. **关键变更请求**：摘 3–6 条与核心闭环相关的 PR 审计（号、标题、结果）。
3. **代表性提交**：摘 5–10 条 feat/fix，对应真实页面或接口。
4. **研发日志摘要**：1–2 段说明联调/缺陷收敛过程，指向 `研发留痕/研发日志.md`。
5. **查阅说明**：写明上述文件在项目内路径，供辅助验证；**不要**写“为了应付检测而生成”。

角色叙述规则与技能正文一致：可用输入的人名，也可用“研发组/测试组”；禁止擅自写用户未提供的公司全称；著作权人未提供不写假名。

## 五、手册撰稿工作流（去 AI 味）

1. **先跑通系统**，按真实点击写步骤（禁止先写空壳再填界面）。
2. **生成/更新 `研发留痕/`**（脚本或手工），输入软件全称 + 团队。
3. **按页写操作**：每步尽量“定位控件 → 动作 → 可见反馈/状态字”；异常写真实提示语。
4. **嵌入开发留痕摘要**（第四节）。
5. **跑限制词扫描**（第二节）与三项雷同测试（第三节）。
6. **通读**：删掉对称排比、空总结、可换行业段落；补版本号与 PR 号。
7. 结果记入 `验收记录.md`；未勾选不得宣称手册完成。

## 六、与下游软著 Word 的关系

- 本规范产出的 `操作手册.md` + `研发留痕/` 是 `software-copyright-deliverables` 的上游事实源。
- 下游排版时可压缩句长、统一四级结构，但**不得删掉**本项目专属控件名、状态词、版本/PR 锚点，不得回退成通用模板句。
- 辅助验证材料以手册摘要 + 项目内 `研发留痕/` 留存为准；是否装订进 Word 附录由下游技能按页数与用户要求决定，**本技能不因下游未附完整仓而省略生成**。
