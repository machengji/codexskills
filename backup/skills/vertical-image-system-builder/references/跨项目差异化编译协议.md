# 跨项目差异化编译协议

本协议解决一个问题：每次系统都要保持相同的交付硬标准，但不能像同一套模板换行业词。它把规则分成两层：**不可变基线**保证质量，**项目变量层**保证每案独立。

## 1. 两层规则

### 1.1 不可变基线（每案必须相同）

以下项目不能为了“看起来不一样”而删减：真实可运行的前后端闭环、鉴权与持久化、中文界面、UTF-8 无 BOM、Three.js/等价三维验收、真实截图与流程态、`设计说明.md`/`验收记录.md`/`操作手册.md`、研发留痕、接口与异常分支、跨项目对照、页面和手册一致性。用户或本技能规定的截图数量、页数、代码文档后端算法占比、WPS 转 PDF、目录和清洁规则也属于基线。

### 1.2 项目变量层（每案重新编译）

变量层不能由“换颜色、换图标、换软件名”构成。每案要从软件全称、现场判断和最近案例指纹编译出一份差异化编译单，并在编码前锁定。变量至少覆盖：

1. 信息架构族与页面顺序；
2. 应用壳拓扑、导航方向和首屏视觉重心；
3. 业务对象、状态机、事件命名和 API 资源拓扑；
4. Store/类型/服务/仓储/三维工厂的文件与函数命名；
5. 三维现场族、装配层级、相机预设和主交互；
6. 色板/字体/材质/纹理/动效节奏；
7. 页面级组件骨架、信息密度和结果区位置；
8. 操作手册章节语法、闭环叙事、异常分类和图注口径；
9. 代码文档的代表性文件排序与章节标题；
10. 截图 `shotGroup` 的状态路径和采集顺序。

## 2. 差异化编译单（必须落盘）

在项目 `_soft_work/variation-manifest.json` 生成一份机器可读编译单，并在 `设计说明.md` 摘要。完成软著整理时，将它移入 `[软件全称]-源代码/研发留痕/差异化编译单.json` 或 `_软著整理备份/`，不把生成期目录留在交付根目录。最小字段如下：

```json
{
  "schema": "variation-manifest/v1",
  "variationId": "由软件全称、项目路径、近案指纹和轮次计算的稳定短哈希",
  "seedInputs": ["软件全称", "核心业务判断", "最近3案指纹", "本轮次"],
  "invariants": ["真实后端", "持久化", "中文界面", "截图/WPS/页数等硬门禁"],
  "selected": {
    "iaFamily": "本案信息架构族",
    "shellFamily": "本案应用壳族",
    "sceneFamily": "本案三维现场族",
    "interactionSignature": "本案标志性交互",
    "manualGrammar": "本案手册章节语法",
    "codeOrder": "本案代码文档排序"
  },
  "forbiddenFromRecentCases": [],
  "reuseLedger": [],
  "differenceScore": {"system": 0, "manual": 0, "code": 0},
  "evidence": ["设计说明.md", "验收记录.md", "研发留痕/", "截图对照"]
}
```

`variationId` 要稳定可复算，禁止用每次随机生成导致返工后换族。推荐计算：`SHA-256(软件全称 + "|" + 核心业务判断 + "|" + 最近指纹ID串 + "|" + 本案序号)` 取前 12 位；本案序号从工作区指纹台账递增分配，同一项目返工沿用原值。`forbiddenFromRecentCases` 至少记录最近 3 案的应用壳、导航、首页轮廓、三维现场族、手册语法和代码目录拓扑；只有用户明确要求换方案时才重新编译。

同一项目的三件套要“事实同源、表达异构”：申请表沿用固定字段格式但重写内容；操作手册的 `manualGrammar` 与代码文档的 `codeOrder` 不得默认相同，除非业务对象确实要求，并在编译单写出理由。这样既能保持名称、状态、模块一致，又不会让三份材料像同一份模板展开。

## 3. 目录只是候选，不是模板

可以从下列候选族中选，但候选名称不能直接变成页面模板；必须把名称中的对象/动作映射到结构和判断：

- 信息架构族：流程脊柱、证据时间线、空间分区、案例棋盘、队列调度、卷宗谱系、指标矩阵、现场巡视。
- 应用壳族：全屏画布、上下分层、右向抽屉、折页工作簿、横向轨道、地图+详情、工具台、事件流。
- 三维现场族：厂站、室内、露天、剖面、台面仪器、卷宗/档案、地形/道路、单机解剖；按名称选择，不能连续默认同一族。
- 交互签名：拖拽时间窗、剖面游标、证据串联、框选联动、状态织带、分屏对照、路径回放、批次锁定。
- 手册语法：任务路线、角色分工、案例叙事、决策树、班次记录、生命周期、异常优先、对象卡片。
- 代码排序：领域事件链、API 合约链、数据血缘链、状态迁移链、算法管线链、对象聚合链。

候选族可扩展；新增族要先写入近案指纹台账，不能只在本案临时命名。

## 4. 差异预算与冷却规则

### 4.1 系统差异预算

把本案和最近 3 个最相似案例逐项对照 12 个轴：信息架构、导航、壳拓扑、首页轮廓、页面顺序、视觉材质、字体层级、图表表达、三维现场族、标志性交互、后端拓扑、业务状态机。对每个近案至少 **8/12 轴不同**，其中首页轮廓、三维现场族、后端拓扑、状态机至少命中 3 轴；不能只靠颜色和文案达标。每轴要写证据，不接受“明显不同”空话。近案少于 3 个时，对照全部可用案例并把本案选择写入基准台账，后续项目按该台账执行冷却。

### 4.2 软著文档差异预算

把申请表、操作手册、代码文档和最近 3 个案例对照 10 个轴：申请表主要功能段、首页定位段、章节拓扑、模块顺序、步骤句式、异常分类、图注口径、研发留痕叙事、代码文件排序、核心函数/类型名。每种文档至少 **6/10 轴不同**；申请表字段顺序和用户指定格式仍按基线固定，不把格式差异当成内容差异。近案不足时按可用案例执行并登记“首案基准”，不得用无历史为由跳过独立编译。

### 4.3 冷却与复用

- 最近 3 案用过的 `shellFamily`、`iaFamily`、`sceneFamily`、`manualGrammar`、`codeOrder` 进入冷却，除非软件全称和现场判断确实要求复用，并写出豁免理由。
- 原子组件、排版 API、错误处理骨架、WPS/截图硬参数可以复用；页面组合、业务模型、状态枚举、路由树、手册章节骨架和代码归档顺序不得整组复用。
- 每次复用都写入 `reuseLedger`：来源、复用范围、为何属于基线/原子层、为避免同构做了什么变化。

## 5. 三项反模板测试（系统和软著都做）

1. **名称删除测试**：删掉软件名，仍能从对象、状态、动作和结果看出本案业务；否则是标题换皮。
2. **行业替换测试**：把行业词换成相邻行业，页面、源码和手册至少有一处结构或状态立即失真；完全可替换则返工。
3. **近案同构测试**：并排看首页缩略图、路由/后端目录树、手册标题序列和代码前 20 个文件；若主要轮廓仅差名词、颜色或文件前缀，差异预算失败。

## 6. 交付前更新指纹

验收最后一轮把本案指纹追加到工作区 `_soft_work/recent-system-fingerprints.md`（或等价台账）：软件名、`variationId`、10/12 轴选择、禁用族、核心状态机、手册语法、代码拓扑摘要和证据路径。台账只保留最近 10 案用于冷却，旧案移入归档，不删除证据。任何返工不得静默覆盖旧指纹。
