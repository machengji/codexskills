# 操作手册规范

本规范用于所有由 `vertical-image-system-builder` 生成或改造的项目。默认交付项目根目录的 `操作手册.md`，目标是让第一次接触系统的业务人员能够按手册完成一次真实可见的业务闭环，而不是只看到一页安装说明。  
**同时必须**满足 [操作手册去AI味与研发留痕](操作手册去AI味与研发留痕.md)：去 AI 腔、防模板/防公开文档雷同，并引用项目内类 GitHub `研发留痕/`。

## 一、交付原则

- 手册内容必须高度匹配软件全称、业务对象、使用者和单点判断，不能直接套用其他行业手册。
- 手册中的页面、字段、按钮、模型部件、影像名称、状态名称和示例数据必须来自当前运行版本。
- 登录页、首页和每个业务页都必须体现该项目独立的业务语境和页面骨架；禁止同一模板只换标题、颜色、数字或图标。
- 手册正文必须本项目专属重写，禁止复用旧案段落批量替换软件名/行业词；这是下游软著文档鉴别材料独创性的前置要求。
- **禁止纯 AI 一次成型的空壳手册**：必须先端到端跑通再写步骤；文风像现场开发/实施写的操作说明，而不是宣传册或生成器输出。
- 每一项操作都要写清“做什么、为什么做、操作后变成什么”，禁止只罗列功能名。
- 用户可见文字使用专业中文；文件使用 UTF-8 无 BOM，中文直接写入，禁止 `\uXXXX`。
- 手册配图以本系统运行截图为主；可说明系统内使用了中国境内真实案例图，但不要用外国图片或无关网图充数。案例来源、中国地点依据与许可细节放在 `设计说明.md` 台账。
- 手册以完整开发者视角组织：体现需求分析、设计评审、开发实现、功能验证、部署上线、文档交付；角色优先使用用户提供的**开发人员/团队**，否则用“需求组/研发组/测试组/部署组/文档组”等统称。**禁止伪造未提供的公司名/著作权人**。
- 默认生成并引用 `研发留痕/`（研发日志、代码版本/提交、PR 审计、版本发布）作为辅助验证材料；最少输入为软件全称 + 开发人员/团队。
- 真实开发：手册中的页面、字段、按钮、状态和流程必须来自当前项目实际运行版本，所有截图只能来自实际运行画面；禁止虚拟图、生图、无关内容或无法端到端走通的流程。

## 二、必备章节

`操作手册.md` 至少包含以下章节：

1. **软件定位**：系统解决的现场问题、适用人员、不适用范围、名称如何对应业务切口。
2. **运行准备**：目录、依赖安装、启动命令、访问方式、停止方式、前端模拟与真实后端的边界。
3. **术语与状态**：核心对象、影像版本、模型部件、处理状态、处置状态、复查状态、归档状态。
4. **页面总览**：全部菜单和页面的职责图，说明页面先后关系而不是只写菜单列表。
5. **逐页操作**：至少覆盖登录和全部业务页面。
6. **核心业务闭环**：从输入到判断、处置、复查、归档完整走通一次。
7. **异常与回退**：空数据、处理失败、误标注、状态冲突、模型加载失败、重复提交等场景。
8. **操作留痕**：哪些动作写入记录、在哪里查看、如何确认回退或复查已生效。
9. **开发留痕**：版本记录、迭代记录、测试记录、验收记录、缺陷修复记录、数据字典和操作留痕说明；并**摘要引用** `研发留痕/` 中的版本发布、变更请求（PR）审计、代表性提交与研发日志；说明每条记录在项目内何处可复查。
10. **模拟边界**：哪些结果是前端确定性演示，哪些接口或算法尚未接入，不得把模拟结果写成真实智能推理。
11. **验收记录**：构建、冒烟、关键链路、三维状态、图表相关性和素材合规结果；含手册去 AI 味与反雷同勾选。

## 三、逐页写法

### 页面自主创新覆盖

登录页必须单独写清业务准入语境、输入字段、验证反馈、失败回退和进入首页后的状态变化；首页及每个业务页必须单独写清页面职责、名称词根、布局/阅读方向、页面专属动作、状态后果和与相邻页面的差异。

“其余页面操作相同”“沿用系统通用页面”“点击后查看结果”等泛化句不能替代逐页说明。如果实际页面只能靠标题区分，先回到 `vertical-image-system-builder` 第一关重做页面，不进入交付验收；若用户另需软著 Word，也必须先把页面异构修到可区分后再调用 `software-copyright-deliverables`。


每个页面至少按以下小节编写：

- **页面目的**：该页负责哪个名称对应的业务判断。
- **进入条件**：需要先完成什么，默认案例或数据从哪里来。
- **界面识别**：说明主舞台、影像、模型、列表、结果区和工具区的用途。
- **操作步骤**：按实际顺序列出点击、拖拽、选择、标注、切换、提交、回退等动作。
- **字段与控件**：逐项说明输入含义、可选值、默认值、禁用条件和校验提示。
- **可见结果**：说明操作后页面、影像、图表（若有）、模型、任务状态或留痕如何变化。
- **页面专属动作**：至少写出该页独有的三个动作及其业务后果。
- **下一步**：说明如何进入下一页面或回到上一步。
- **常见问题**：至少列出一个容易误操作的点和处理方式。

图表只在确有业务判断时写入手册，并必须说明数据来源、读图结论、点击联动和结果后果；没有这些内容的 chart 不应出现在页面或手册中。

## 四、核心闭环写法

至少用一份编号流程写清：

1. 载入与确认业务对象；
2. 查看或处理现场影像；
3. 添加、修改或撤销重点标注；
4. 进入名称对应的三维模型，切换视角和业务状态；
5. 根据影像、模型和必要的证据数据作出判断；
6. 提交处置、方案或复查任务；
7. 查看状态变化、处理结果和操作记录；
8. 执行复查、回放或归档，并说明如何确认闭环完成。

每一步都要写明前置状态、触发动作、可见变化、失败处理和下一步入口。

## 五、异常、回退与留痕

至少覆盖：

- 影像为空或素材不合规；
- 处理步骤失败或需要重试；
- 标注误操作后的撤销与恢复；
- 业务状态冲突或重复提交；
- 三维模型未加载、部件选择无结果或状态切换失败；
- 复查结果不通过时如何回到处置；
- 刷新页面后哪些状态保留、哪些状态仅为本地演示。

说明每种异常的提示文字、阻断动作、回退入口和记录位置。

## 六、截图与素材要求

- 关键页面优先使用当前项目实际运行截图；截图应能看到真实页面、按钮和状态变化，并在手册中配图注。
- 截图路径必须指向项目内文件，图片名称与页面职责一致。
- 手册不得使用外国图片或无关网络图片充数；系统业务区内的真实案例图须为中国境内场景、已本地化并可在界面操作中看到。没有合规运行截图时，可使用页面结构说明和本地演示画布，但要明确标注。
- 每张图只证明一个操作或状态，图注写清“操作前/操作后”和验证结论。
- **同页步骤必须有实质交互**：需要连续截图的步骤，优先在每一步打开并保持可见的弹框/抽屉/详情面板，执行字段变更、筛选、选中、提交或状态操作；弹框及其结果必须改变至少两个可见区域，并在 `shotGroup` 记录 `stepId`、操作名与变化区域。
- **高清 2x**：使用 viewport `1440×900`、`deviceScaleFactor: 2` 采集（约 `2880×1800`）；等待字体、数据、弹框和三维/影像联动稳定，原图宽度不得低于 2400px，100% 查看时中文和控件必须清晰可读。
- 所有截图必须来自当前项目实际运行画面；禁止生图、虚拟图、无关网图冒充真实界面；手册中每条流程都必须能按步骤端到端走通，走不通的流程不得写入手册。

## 七、去 AI 味与反雷同

完整词表、三项测试与撰稿工作流见 [操作手册去AI味与研发留痕](操作手册去AI味与研发留痕.md)。此处为强制摘要：

1. **禁用**：综上所述、值得注意的是、本章将介绍、如下所示、一站式赋能、文档制作/配图策略等元叙述与宣传腔。
2. **限制**：首先/其次/最后、闭环/赋能/高效/一键——必须绑定真实控件、状态或数据结果，整本合计慎用。
3. **必做测试**：换行业测试、同级案例换词测试、公开通用文档雷同清理；结果写入 `验收记录.md`。
4. **写法**：每步尽量“菜单/按钮定位 → 动作 → 可见反馈”；异常抄真实提示语；可穿插版本号与 PR 号增强真实开发感。
5. 页与页之间禁止同一套空壳小节只换业务词；相邻页专属动作与异常类型必须可区分。

## 八、研发留痕写入手册

1. 交付前必须存在项目根 `研发留痕/`（可用 `scripts/generate_dev_forge.py`，输入软件全称 + 开发人员/团队，可选著作权人）。
2. 在「开发留痕」中至少写入：
   - 当前交付版本与发布日期（引自 `版本发布记录.md`）；
   - 3–6 条已合并 PR（号、标题、测试门禁结论）；
   - 5–10 条代表性提交（feat/fix 与模块名）；
   - 1–2 段研发日志摘要（联调/缺陷收敛）；
   - 查阅路径：`研发留痕/` 相对项目根的路径说明。
3. 留痕是**辅助验证材料**：增强“真实团队开发”观感；不得在正文声称已托管到外网 GitHub，除非用户提供真实地址。
4. 模块名、页面名必须与当前系统一致；禁止跨项目复制 PR 标题后换词。

## 九、交付前核对

- [ ] 软件定位、名称语义和单点业务切口明确。
- [ ] 安装启动、页面总览和术语状态完整。
- [ ] 登录页有独立的业务准入语境，不是通用登录模板换肤。
- [ ] 登录及全部业务页面均有逐页说明，且每页的职责、专属动作和状态后果均不同于模板化换皮。
- [ ] 反换词/独创性：手册叙述不能套到其他行业软件上仍成立；无旧案换词痕迹。
- [ ] 去 AI 味：禁用词清零；限制词未滥爆；无元叙述/万能宣传。
- [ ] 反雷同三项：换行业、同级换词、公开通用句清理均通过，并记入验收记录。
- [ ] `研发留痕/` 七件套齐全；手册已引用版本/PR/提交/日志；输入含软件名与开发人员/团队。
- [ ] 核心闭环从输入到归档可按手册走通。
- [ ] 每页有前置条件、步骤、结果、专属动作和异常处理。
- [ ] 图表只在必要时出现，且图表数据来源、判断和联动写清。
- [ ] 手册无无关网图充数；运行截图来自项目内；真实案例图来源可在设计说明台账追溯。
- [ ] 三维模型、视角、状态、部件联动与手册描述一致。
- [ ] 模拟边界、已知限制和操作留痕如实说明。
- [ ] 手册以完整开发者视角组织，含开发留痕；角色为用户提供的开发者或统称，无伪造公司/著作权人。
- [ ] 截图与流程全部来自当前项目真实运行，核心链路端到端走通，无虚拟图/生图/无关内容。
- [ ] 手册至少经过三轮从头到尾的实际操作复核；未全绿时继续修复，不以“没有新增问题”替代全部门禁通过。


## 禁止正文写文档制作说明（强制）

- 手册正文只写业务：功能、步骤、结果、异常、回退、边界与可公开的开发留痕摘要。
- 禁止写入“纯文字首页/配图策略/进入态与操作后态/避免后文无图/培训提示/全书看图路径/去 AI 检测策略”等制作说明。
- 图注只写界面名称或业务状态，不写生成要求。
- 制作门禁留在 skills 中执行，不进入用户手册正文。
