# 软著操作手册与垂直系统一体化生成（合并技能）

> 本技能由 `vertical-image-system-builder` 与 `software-copyright-deliverables` 合并而来，取代两者作为独立入口。  
> 最终目标：生成一本**反模板化、截图状态链多态、每图配 3–5 行短人话说明**的软著操作手册，并完成软著三件套交付。  
> 默认在当前 Codex 会话（Windows + PowerShell）中直接建项目、写代码、启动运行、按清单验收、失败即修，循环直到达标；除非用户明确说“只要提示词 / 不要写代码 / 给 AI Studio 用”。

## 技能定位与边界

- 本技能**独立负责整条链路**：垂直系统设计实现 → 真实运行验收 → 研发留痕 → 截图采集 → 申请表 → 代码文档 → 操作手册 Word → 目录收敛（不产出 PDF）。
- **每案开工前先读 [实战踩坑与脚本复用](references/实战踩坑与脚本复用.md)**：环境硬坑、截图返工根因、页数调法、可复用脚本清单全在里面，可省掉大量返工。
- 视觉精修强制接入 `frontend-design`（见 [frontend-design接入](references/frontend-design接入.md)）；三维高完成度强制接入已安装的 `threejs-*` 技能包（见 [Three.js高级建模技能接入](references/Three.js高级建模技能接入.md)）。
- 真实网图案例默认启用（中国境内硬门禁），细则见 [真实网图案例规范](references/真实网图案例规范.md)。
- **硬门禁之外全部是变量层**：技术栈、页面数量、模块结构、源代码文件格式、手册章节语法、截图状态链、研发留痕文件结构每案必须重新编译，禁止连续两案同构。

## Codex 运行环境（本机硬事实）

- 运行宿主：Codex 桌面版，Windows + PowerShell（pwsh 7.6），默认工作根 `E:\已完成的案例-可做参考` 或用户指定项目路径；所有命令经 `exec_command` 执行，不依赖其他平台会话。
- 文件编码：所有产出 UTF-8 无 BOM，禁止 UTF-16/GBK；中文直接写，禁止 `\uXXXX` 转义；写入用 PowerShell `[IO.File]::WriteAllText($path,$text,[Text.UTF8Encoding]::new($false))` 或 Python `open(..., encoding="utf-8")`。
- 运行栈：Node v20（`node`）、Python 3.11（`python`）；`npm run dev` 用 exec 会话后台启动并记录端口，验收后停掉 dev server。
- **启动 dev server 的硬坑**：Windows 下 `Start-Process -FilePath "npm"` 起不来（日志为空、端口不通），必须直接调 node 跑 vite 入口：
  `Start-Process -FilePath $node -ArgumentList "`"$vite`"","--port","5211","--strictPort"`，其中 `$vite = <项目>\node_modules\vite\bin\vite.js`。
- **探端口不要靠日志**：日志常为空或滞后，用 `New-Object Net.Sockets.TcpClient` 连接测试；「启动」与「探测」拆成两次工具调用，串在一条命令里有时会返回 `Unknown: ChildProcess.kill` 而无输出（但服务其实已起）。
- **测页数唯一可靠方式是 Word/WPS COM**（`ComputeStatistics(2)`）；LibreOffice 对中文路径会静默失败，不要指望它。可复用脚本 `_soft_work/_pages.ps1`（测页数）与 `_topdf.ps1`（导 PDF 供逐页渲染检查，交付目录不留 PDF）。
- 截图采集（硬性：每案至少采集 40 张不同状态截图，禁止用同屏近似图凑数）：优先 in-app Browser / Chrome 控制 / `node_repl` 的 Playwright 打开 dev server 页面采集；浏览器已预装（系统 Chrome → Edge → 缓存 Playwright Chromium），禁止每次 `npx playwright install`。
- **截图前必须先重置数据库**（最大返工根因）：反复跑截图脚本会让库停在中间态，导致后续操作「已是目标状态」、点击后无变化；症状是 toast 提示成功但状态列不变。写重置脚本直接调项目 seed。
- **输入框定位别用 `input[type="number"]`**：`v-model.number` 渲染出来是 `type="text"`；用 `.stage input` 配 `nth(i)` 按位置定位，并先用 probe 脚本打印 `evaluateAll` 的 name/value 确认索引，避免错位。
- 三维技能：已装 `E:\machengji\.dsh\skills\threejs-*` 全套，编码前按 [Three.js高级建模技能接入](references/Three.js高级建模技能接入.md) 路由阅读。
- PDF 转换：**不使用 WPS 转 PDF**，交付不产出 PDF。
- 技能自带脚本：`scripts/validate-code-doc.ps1`（pwsh 直接跑）、`scripts/check_china_case_ledger.py` 与 `scripts/generate_dev_forge.py`（`python` 跑）。
- **可复用脚本模板在 `scripts/templates/`**（从水利案固化，含截图采集、代码文档生成、操作手册生成、测页数、导 PDF、空白量化、差异检查、重置数据库、重建 manifest 共十个脚本），用法与占位符对照见 `scripts/templates/README.md`；复制到本案工作目录后替换 `{{占位符}}` 即可用。
- 读图/视觉验收：截图内容用 `vision-analyze` 技能 CLI 或本机 agent-vision 代理（`http://127.0.0.1:19100/v1`）识别，禁止以“模型不支持图片”推脱。

## 硬门禁（强制，冲突时取更严者）

### 1. 真实开发与真实截图
- 手册只能描述当前项目**实际可运行**的系统；所有截图只能来自当前项目实际运行的浏览器/客户端画面；禁止虚拟图、生图、无关图片、拼接或改图。
- 核心业务闭环必须端到端跑通后才能写入手册；跑不通的流程不得写入手册。
- 代码文档以代码为主，**代码中不保留任何注释（中英文全部去掉，只留纯代码）**：生成/整理代码时注释一律删除，只保留纯代码；不参与运行的算法说明可单独生成并标注“说明性内容，不参与运行”，但不能替代真实源码，也不得挤占后端/算法代码的前部位置。

### 2. 反模板化 / 跨项目差异化编译
- 系统与最近 3 案比较 12 轴，每案至少 8/12 轴不同；软著每种文档比较 10 轴，至少 6/10 轴不同。
- 反模板化只做内部自查，**不产出差异化编译单等落盘文件**；用稳定 `variationId` 记入工作区近案指纹台账即可；禁止复制旧项目后批量替换关键词。
- 编码前必须读取 [跨项目异构与反流水线](references/跨项目异构与反流水线.md)；12 轴/10 轴差异预算按本技能“硬门禁 2”执行。
- 登录页、首页和全部业务页面均有独立职责与专属操作记录，未使用同一页面模板换肤。
- **手册开头格式轴（强制）**：操作手册首页开头段格式与整本叙事方向每案自主编译，禁止连续两案同构（如四段标签式「业务定位/适用角色/单点判断/不适用范围」不得连续两案复用）；生成前先读工作区近案指纹台账选方向，定稿后按台账复核，方向族+方向描述两字段都查。
- **台账维护**：定稿后往 `recent-system-fingerprints.md` 追加正式条目（`variationId`、信息架构、应用壳、首页轮廓、三维族、后端拓扑、前端栈、手册方向、签名元素、状态机、色板、交付数据、禁止后续近案复用清单），并**删掉阶段一留下的「（在建）」条目**，否则台账重复、后续选方向时会误判。删除时用**按行切片**而非字符串 replace——文件换行符（CRLF/LF）差异会让 `Contains` 匹配失败。

### 3. 截图状态链多态协议（核心，生成期前置）
> **生成期前置（强制）**：状态链不是截图阶段临时摆拍出来的，而是**系统一开始生成时就要按这个方向写代码**——
> 每个菜单/页面都必须有真实可操作的业务逻辑，操作后页面必有可见变化（弹框/抽屉/详情面板/提示/toast/列表刷新/状态列更新/联动等），禁止静态页面。
> 先按本项目业务自主编译操作链（进入 → 输入/选择 → 触发 → 系统计算/状态变更 → 反馈），再按链编码；截图只是把代码里已有的真实状态变化录下来。
- 每个功能模块的截图必须按真实操作链编排，形成状态链；每一张截图都是执行某一步操作之后的可见新状态。
- **状态链由本项目真实业务流程编译，不套固定链**：先梳理本案真实操作链（如 登录→筛选→提交→审核→归档、上传→识别→结果→导出→删除、切换工况→联动→告警→处置 等），再决定截图顺序。示例 `空白/初始页 → 输入凭据或参数 → 系统评估/计算出结果 → 导出弹窗 → 删除/归档后列表变化` 仅作示意，禁止照抄。
- 同组相邻截图差异必须肉眼可辨，且来自真实业务后果；只出现时间、数字、光标、轻微滚动或短暂 toast 的截图删除并重走流程。
- 同组至少 1 张含弹框/抽屉/详情面板并保持可见；结果态至少两个业务区域变化。
- 每张截图登记 `stepId`、`shotGroup`、`action`、`beforeState`、`afterState`、`visibleChanges`、`popup`。
- **步骤与截图严格一一对应**：手册中每个操作步骤都必须有对应截图，截图紧跟对应步骤；禁止无截图的长步骤清单（如「XX操作清单」1.2.3.4.5 连续编号步骤）。纯说明、异常拦截、数据字典、环境部署、附录等非操作步骤内容可无图。
- 采集规格：页面按 **1920 宽度设计**，viewport `1920×1080`、`deviceScaleFactor: 1.5`（约 `2880×1620`），原图宽度 ≥2880px，100% 可读。
- **采集顺序不可颠倒：先重置数据库 → 再按状态链操作 → 边操作边录元数据**。反复跑截图脚本会让库停在中间态，导致后续操作「已是目标状态」、点击后无变化（症状：toast 提示成功但状态列不变）；这是最常见的返工根因。
- **操作起点要选「有变化空间」的状态**：初始已是「已锁定」的单据再点锁单看不出变化；应先切到初始「对账中」的记录再操作。
- **差异判定标准是「状态确实变了」，不是像素占比高**。变化常集中在状态列/判定框/计数区等局部，整图占比可能仅 0.2%，属正常。核对项：toast 文字、状态列文字、指标计数、判定框配色、留痕条数、三维着色。用像素差异脚本先筛出 <1.2% 的组，再**逐张肉眼核对**确认。
- 细则见 [操作手册截图状态链协议](references/操作手册截图状态链协议.md)；实操坑见 [实战踩坑与脚本复用](references/实战踩坑与脚本复用.md)。

### 4. 每图 3–5 行短人话说明（核心）
- 每张截图在手册正文中配 **3–5 行**人话描述，禁止长篇大论、禁止 AI 腔、禁止元叙述。
- 说明固定回答两个问题：① 这个页面是执行哪一步操作之后得到的（操作入口 → 动作 → 页面反馈）；② 页面主要元素用途（各区域/按钮/字段是干什么的）。
- 图注只写业务界面名或状态名，如 `评估结果页`、`导出弹窗-已选 3 条`、`删除后列表-剩 2 条`。
- 同一完整句子在全手册最多出现 1 次；允许专有名词重复，不允许整段模板句重复。
- **禁止无截图步骤清单**：正文不得出现连续编号、无对应截图的操作步骤清单；步骤要么配图，要么并入已配图小节的正文描述。

### 5. 操作手册去 AI 味与研发留痕
- 遵守 [操作手册去AI味与研发留痕](references/操作手册去AI味与研发留痕.md) 与 [去AI味自然写作编译规范](references/去AI味自然写作编译规范.md)。
- 禁用总结腔、元叙述、万能宣传、AI 腔；完成换行业 / 同级换词 / 公开通用句三项检查。
- 手册必须包含“开发留痕”章节：版本记录、迭代记录、测试记录、验收记录、缺陷修复记录、数据字典、操作留痕，以及版本发布 / PR 审计 / 代表性提交 / 研发日志摘要（引自 `[软件全称]-源代码/` 内的留档子目录，目录名每案自主编译，禁止固定叫「研发留痕」）。
- 角色优先使用用户提供的开发人员/团队；未提供时用“需求组/研发组/测试组/部署组/文档组”等统称；禁止伪造未提供的公司名/著作权人。

### 6. 代码文档后端/算法主体优先（以代码为主）
- 代码文档**前半部分（前 50% 页码）绝大多数必须是后端/API、鉴权、领域服务、规则引擎、状态机、数据处理算法、数据模型与持久化等真实代码**，前端页面交互代码一律放到后部，禁止前部被前端代码或说明文字占据。
- 后端与算法逻辑类源码按有效源码行数统计必须占代码文档实质源码 **≥85%**，前 50% 页码主要由后端/算法代码组成。
- **前端样式代码与页面结构代码一律不进代码文档**：CSS/SCSS/LESS 等样式文件、HTML 模板、Vue/React 页面组件（template/JSX 布局）等不得编入；仅允许保留少量前端算法逻辑（如三维场景构建、数据变换、图表计算），且计入后仍须满足后端+算法逻辑占比 ≥85%。
- **以代码为主，代码中不保留任何注释（中英文全部去掉，只留纯代码）**：生成/整理代码时注释一律删除，只保留纯代码，注释行不得用来凑页数。
- Word/WPS 实测约 70 页（允许 66–75 页，优先 70 页左右），空行/硬分页为 0；禁止同构模板凑页。
- **代码 Word 不设置页眉/页脚/页码**：正文只放纯代码，禁止页脚、页码、页眉及任何非代码文字；上下/左右边距保持紧凑（建议 18–20mm），禁止用 47mm 之类大边距制造每页顶部/底部大片空白；收紧边距后仍须 Word/WPS 实测约 70 页且后端+算法逻辑占比 ≥85%。

## 工作流程细节

### 阶段一：系统生成与验收
1. **第一关（先于任何代码）**：名称编译（软件全称逐字锁定，页面显示与用户提供名称完全一致，禁止简写/改字/英文替代）、三案竞争、frontend-design 精修、登录页/全页自主创新、跨项目防重复、`variationId` 与 12 轴差异预算（反模板化只做内部自查，不产出差异化编译单文件）。未通过不得批量写页面。
2. **独有业务切口**：从系统全称推导核心对象、主要使用者、最关键现场问题、影像能发现什么、三维能说明什么、输入到复查归档的闭环；选单点纵深，不做通用后台。
2-A. **动态交互与操作反馈编译（生成期前置，强制）**：编码前先按本项目业务为每个菜单编译操作链（进入 → 输入/选择 → 触发 → 系统计算/状态变更 → 反馈），并把“操作后页面必有可见变化”作为编码硬要求：弹框/抽屉/详情面板、toast/提示、列表刷新、状态列更新、三维/图表联动，每菜单至少 2 处可见变化；禁止静态页面、占位按钮、点了没反应或只换数字/toast 的假交互。截图状态链只是这些真实变化的录制，不是截图期补摆拍。
3. **高完成度三维**：按 [Three.js高级建模技能接入](references/Three.js高级建模技能接入.md) 路由，达到“现场级可运营”质量（整厂/产线/仓储观感），数字只作参考；三维至少落在 3 个菜单，每个菜单至少 1 种不同模型（如 整场总览 / 单机近景 / 剖切或路径预演），禁止不同菜单共用同一模型只换色/换视角。
4. **真实网图案例**：中国境内真实网图本地化 ≥6 张，覆盖 ≥3 个业务页；台账记录来源、许可、`country: 中国`、省市地点、地点依据、名称词根、使用页面、业务角色；禁止外国图片补位。
5. **运行—验收—修复循环**：构建、冒烟、关键链路、三维状态、图表相关性、素材合规、反换词源码对照、页面缩略拼图、三轮验收；未全绿不得进入截图/文档阶段。
6. **留档目录（研发留痕）**：目录名/文件名/内容由软件全称自主编译（用 `scripts/generate_dev_forge.py --project . --name <软件全称> --team <团队>`，默认不再生成固定「研发留痕」名；至少含研发日志、提交记录、PR 审计、版本发布四类），生成后按本案模块手工修订，禁止直接照搬默认文案；有真实 git 优先提取真实历史。留档目录放在 `[软件全称]-源代码/` 内（生成时用 `--dir-name "<软件全称>-源代码/<留档子目录名>"` 直接落在源代码目录内，或生成后移入），不单独放在项目根级；设计说明、验收记录、操作手册.md 源稿等所有留痕文件交付前一律移入该留档子目录。

### 阶段二：截图采集（状态链多态）
1. **先复用，后补截**：扫描 `_soft_shots/`、`_soft_tmp/screenshots/`、历史 `DELIVERED_DOCS/screenshots/`；已有足量、高清、文件名语义可用的截图直接复用，只对缺失模块/状态做增量截图；禁止每次任务开始就删除缓存目录。

- 禁止同屏近似图：换时间、换数字、轻微滚动、短暂 toast 都不算新状态。
- 截图文件名语义化，如 `s01-login`、`s12-efficiency-result`。

### 3. 手册文字
- 正文中文字符建议 ≥8000 字，覆盖登录、总览、各业务页、异常回退、数据字典、接口验证、角色权限、FAQ、开发留痕。
- 每张图配 3–5 行短人话说明，回答“哪步操作后得到此页”和“主要元素用途”。
- 清除模板句：不要写“本页只记录一次操作”“下一步继续沿同一条业务链执行”“状态一截图”等制作说明。
- 清除硬性措辞：正文里“必须/不得/禁止/不允许”改为“需要/不会/不应/暂不支持”。

## 并行多案（2026-09-11 四案并行固化）

多案并行时每案开一个独立对话，**首条派活消息必须自包含**（对方看不到本会话上下文）：

1. 指向工作区的交接说明文件（含环境、坑、门禁、可复用脚本索引）。
2. 该案已知信息：技术栈、前后端端口、后端入口与启动命令、测试命令、登录凭据与登录路由、页面清单、三维模型清单、网图数量。
3. 交付目标八步，与本技能门禁对齐（收口 → 密度返工 → 截图 → 留档目录 → 申请表 → 代码文档 → 操作手册 → 目录收敛）。
4. 关键坑提示，至少含「截图前重置数据库」「输入框定位别用 `input[type=number]`」「差异判定看状态变化不看像素占比」。

**教训**：交接消息里的路径不要手打，容易写错（曾把截图输出路径写错只能补发更正）；应从项目实际目录复制路径。另外对方回合可能「结束但无可带回文本」，此时**直接检查项目目录的实际产物**（截图张数、DOCX 是否存在、根目录是否收敛）来判断进度，不要等回信。

派活后主对话可继续推进自己那案，用 `contacts` 查看各会话忙碌/空闲状态，用产物目录核对实际进度。
