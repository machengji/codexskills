> **技能定位**：本技能是**独立的**软著交付技能，负责申请表、代码文档、操作手册 Word 与源码目录整理。`vertical-image-system-builder` 是另一独立技能，只负责垂直系统实现；两者并列协作，**不是**“一个总控技能 + 一个兼容入口”。用户只要软著时直接使用本技能；用户只要系统实现时不要自动进入本技能。

## 用户通用修改要求（强制，适用于新做与返工）

以下要求是所有申请表、操作手册、代码鉴别材料和目录整理任务的共同基线；与本技能其他条款冲突时，采用更严格的一项：

1. **以真实业务流程为主**：减少泛泛的功能介绍，优先描述真实对象、操作任务、判断结果和后续责任。
2. **步骤必须可执行**：每个操作步骤都写清“操作入口 → 执行动作 → 页面反馈”，必须出现真实菜单、按钮、字段、状态或结果名称。
3. **增加有后果的交互**：优先覆盖提交、校核、审核、派发、回退、复查、锁定、导出、归档等会改变状态、数据、责任或版本的动作。
4. **模块结构完整**：每个功能模块必须包含前置条件、详细步骤、异常拦截、恢复方式和本章验收结果；不得只写功能简介。
5. **截图服务于流程**：截图必须来自当前项目真实运行，优先使用筛选后、提交后、校核后、审核后、状态变更后、导出后或归档后的流程态，避免只展示静态首页或大屏；同一组截图必须能看出真实操作及其页面后果。
6. **截图清晰且唯一**：截图应完整、可读、与步骤对应；同一截图在手册中只引用一次，禁止重复使用、拼接或混入无关页面；同一模块内的截图不得只是同一画面换时间、换数字或换滚动位置。
7. **手册文案去模板化 / 去 AI 味**：避免重复句式、宣传语、AI 腔、总结腔、元叙述和制作过程说明；同一完整句子不得批量复制后仅替换序号或业务名词；必须通过换行业、同级换词、公开通用句雷同三项检查（正面写法见 R23-F，细则见 [操作手册去AI味与研发留痕](references/操作手册去AI味与研发留痕.md)）。
8. **全称逐字一致（强制）**：申请表、操作手册、代码文档封面与正文、目录名、页眉页脚、PDF 水印中出现的软件名称必须与用户提供的软件全称逐字一致，禁止简称、缩写、别称或“××工作簿/工作平台/分析系统”等替代；全称过长可分行或缩小字号，但不得省略或改写任何字；软件名称一律中文原文直接写入，禁止 Unicode 转义写法。
9. **研发留痕可验证**：优先复用或生成项目内 `研发留痕/`（类 GitHub：研发日志、提交记录、PR 审计、版本发布），并把版本/PR/提交摘要写入操作手册开发留痕；最少输入软件全称 + 开发人员/团队，著作权人可后补。
10. **源码材料后端与算法主体优先**：代码文档前部先展示后端/API、鉴权、领域服务、规则引擎、状态机、数据处理算法、数据模型与持久化，再展示对应业务页面交互；后端与领域算法类源码按有效源码行数统计必须占代码文档实质源码至少60%，前50%页码必须主要由这些代码组成；前部不得被通用布局、样式或配置占据。
11. **每个新项目系统与手册不得与旧案类似**：UI、源码拓扑、操作手册章节与步骤须与最近案例明显异构；禁止旧案换词交差。
12. **降低低代表性代码占比**：通用样式、依赖配置、锁文件、脚手架、reset CSS 和无业务语义的重复配置只能后置或剔除，不得用于凑页。
13. **三件套保持同源**：申请表、操作手册和代码文档必须使用一致的软件名称、业务对象、页面术语、状态名称、判断链路和成果口径。
14. **执行完整技术验收**：交付前检查 UTF-8 无 BOM、TXT 无空行、DOCX 无空段和硬分页、目录正常、截图唯一、同组截图状态差异、页数达到要求、手册去 AI 味与研发留痕引用、代码前部后端算法占比、WPS 转 PDF 结果，并完成真实排版引擎实测。
15. **最终清理交付目录**：移除或备份临时脚本、依赖目录、构建产物、生成期代码 TXT、重复文档、无关 PDF、`DELIVERED_DOCS` 残留和 Windows 垃圾文件；项目根最终只保留标准交付六项（申请表 TXT、代码 DOCX/PDF、手册 DOCX/PDF、源代码目录；`研发留痕/` 可随源码目录或备份保留）。
16. **代码文档纯净性（强制）**：代码 Word/TXT 只收录真实源码与 `// 文件归档: [相对路径]` 归档头；**禁止**在代码文档中加入“源程序鉴别材料”“版本：V1.0.0”等头部说明、`// 说明：带“说明性内容，不参与运行”标记的段落…` 解释句，以及“说明性内容，不参与运行 / 领域说明 / 规则索引 / 数据处理说明 / 测试摘要 / 后端边界索引”等填充段；算法说明如需保留只能放操作手册附录，不得混入代码文档。**只收代码不收文字**：代码文档只收录真实代码文件（.py/.ts/.vue/.js/.css/.html/.json 等），`algorithm_notes.md`、`设计说明.md`、`README.md` 等算法说明/设计/文档类 markdown 一律不进代码文档（可留在源代码目录或操作手册附录）；空行直接跳过，**禁止**生成 `// 空行已省略` 等占位文字；除 `// 文件归档:` 归档头外不得出现任何非代码说明文字。

## 文档前置门禁（进入文档前核对）

在读取截图、生成申请表或编写 Word 之前，先按项目类型核对证据：

### A. 普通既有项目（默认）
1. 项目路径、软件全称、可识别源码与可运行入口明确。
2. 截图来源属于当前项目；页面按钮尽量对应真实可见后果。
3. 不得伪造未运行页面的截图，也不得用文档页数掩盖功能缺失。

### B. 来自 `vertical-image-system-builder` 的项目（额外核对）
1. `设计说明.md`：包含软件全称拆解、三套候选方向及评分/淘汰理由、名称语义映射、UI创新指纹、登录页独立性记录、逐页异构矩阵、页面重复预算、同级案例十维差异和单点业务链路。
2. `验收记录.md`：包含至少两轮前置设计审查，以及后续运行、交互、视觉缩略拼图、跨项目对照、三维（如适用）、**手册去 AI 味与反雷同**验收记录。
3. 登录页、首页和每个业务页均有独立的页面职责、主体轮廓、专属动作和状态反馈；不能只有同一模板换标题、颜色、数字。
4. 项目已经实际启动并能打开；截图来源属于当前项目。
5. 优先存在 `操作手册.md` 与 `研发留痕/`；若缺失，文档阶段按 R23 补齐类 GitHub 留痕摘要后再写 Word，不得空写“已完成测试/已合并 PR”。

缺少证据时：
- 若用户同时要求新建/改造系统：先切换到 `vertical-image-system-builder` 完成系统实现与验收，再回到本技能；
- 若本次只要求整理既有项目文档：不能擅自大改业务代码，但必须如实记录证据缺口，文档不得宣称系统已完成或已达标。

**文档阶段的退出条件不是“文件成功写出”，而是：文档内容、Word/WPS 排版、截图真实性、鉴别材料独创性/代表性与最终目录全部通过。**

## 鉴别材料独创性与反模板化硬门禁（强制，R21）

> 高频补正原文对应：  
> 1）“提交的文档和源程序鉴别材料模板化程度较高，请提交具有独创性、代表性的文档和源程序鉴别材料。”  
> 2）“提交的源程序鉴别材料中出现大量与已登记或申请的软件源程序鉴别材料重复或雷同的内容，批量替换了关键词，请提交独立开发的程序及其有关文档的鉴别材料。”  
> 本技能生成申请表、代码文档、操作手册时必须主动规避以上补正，不得只满足页数与格式。

### R21-0. 固定基线与项目变量分离（新增强制）

本技能把“必须一样的格式/质量”与“每案必须不一样的内容/叙事”分开管理。先读取 [跨项目差异化编译协议](../../vertical-image-system-builder/references/跨项目差异化编译协议.md)；路径不可读时按本节规则执行，并在项目内生成一份等价编译单。

**不可变基线**：申请表字段结构与用户指定版式、UTF-8 无 BOM、申请表/代码 TXT 无空行、代码文档连续排版且实测至少 66 页、后端/API/领域算法有效源码至少 60%、操作手册文字首页和 51–60 页、真实高清流程态截图、WPS 直转 PDF、三件套同源、目录六项清洁、开发留痕、去 AI 味和真实运行证据。这些要求每案保持一致，不得用“创新”名义删减。

**项目变量**：从当前系统的 `设计说明.md`、`验收记录.md`、源码、截图和最近 3 个案例编译申请表内容、手册章节语法、步骤顺序、异常分类、图注口径、研发留痕叙事、代码文档排序、核心函数/类型名和 `shotGroup` 路径。颜色、软件名、图标、文件前缀和序号变化不算变量。

三件套遵循“事实同源、表达异构”：申请表格式可以固定但内容必须重写；操作手册章节语法与代码文档排序默认不得相同，除非本项目业务确实要求并在编译单中写明理由。

在 `_soft_work/variation-manifest.json`（或已有 `研发留痕/差异化编译单.json`）记录：`variationId`、不可变基线、已选文档语法、最近案例禁用项、复用台账、申请表/手册/代码的差异分数和证据路径。软著整理后把编译单放入 `[软件全称]-源代码/研发留痕/` 或 `_软著整理备份/`，不能把 `_soft_work` 留在最终根目录。返工沿用原 `variationId`，不得每轮偷偷换结构。

**软著差异预算**：与最近 3 个案例按 10 个轴对照——申请表主要功能段、首页定位段、章节拓扑、模块顺序、步骤句式、异常分类、图注口径、研发留痕叙事、代码文件排序、核心函数/类型名——每个文档至少 **6/10 轴不同**。近案不足 3 个时按可用案例执行并登记首案基准。申请表字段顺序和用户指定格式仍固定，不把格式变化冒充内容差异。最近 3 案使用过的手册语法、代码排序、章节拓扑进入冷却；确需复用必须写豁免理由并做结构性改造。

**三项测试**：删除软件名仍能辨认业务对象与判断；把行业替换为相邻行业后正文/步骤/源码排序立即失真；并排看近案首页定位、标题序列、代码前 20 个文件和异常表，不能只差名词/颜色/文件前缀。任一失败，停止生成并回到 R21-B/R21-C/R21-D 重编译。

### R21-A. 总原则
1. **格式可参考，内容必须独立**：可参考用户指定的申请表/手册**字段结构与排版格式**；正文内容、功能叙述、步骤、截图、源程序摘录必须来自**当前项目独立实现**，不得沿用其他已登记/已申请/同级案例的正文骨架后只换软件名、模块名、行业词。
2. **禁止批量替换关键词**：禁止把旧项目材料中的“对象/场所/模块/状态/按钮/变量/文件名”整批替换成新词后当新材料；若与同级案例对照后，主要功能段、手册章节骨架、代码归档文件集合或核心函数命名仅有词面差异，判定失败并重做。
3. **必须具有独创性与代表性**：
   - 独创性：能看出本软件自己的业务切口、页面职责、数据对象、判断链路与实现结构；
   - 代表性：鉴别材料优先展示本软件核心业务实现，而不是通用脚手架、依赖配置、空壳路由或可跨项目复用的模板段落。
4. **三件套同源独立**：申请表主要功能、操作手册章节、源程序鉴别材料必须描述同一套本项目真实模块；任一件能套到另一个无关行业软件上而不违和，即判定模板化失败。

### R21-B. 申请表内容独创性
1. 第11–14项必须按本软件真实痛点、领域、模块、技术实现重写；禁止复用固定句式只替换行业名词。
2. 第13项主要功能必须点名本项目真实菜单/页面/对象/状态流转/结果沉淀，至少覆盖 5 个本项目专属模块，不得写成“用户管理/权限管理/数据统计/系统设置”等可任意替换的空壳。
3. 第14项技术特点必须对应本项目真实技术选型与实现点（如本项目状态机、三维联动、影像标注、规则引擎等），禁止通用“前后端分离、模块化、高可用”套话堆砌。
4. 若同目录或用户指定范围内存在其他软件申请表，生成后必须做一次**跨项目抽检**：主要功能连续 80 字以上不得与他案高度同构；同构则重写。

### R21-C. 源程序鉴别材料独创性与代表性（后端算法主体优先）
1. 代码文档必须来自当前 `[软件全称]-源代码/` 的真实独立开发文件；禁止从其他软著包、其他项目代码 Word/TXT、或“旧案换词版”源码复制后改名。
2. **代表性优先收录顺序（强制，前部必须是后端与业务逻辑）**：
   1) **后端/服务端入口与 API 路由、鉴权、请求校验、统一错误处理**；
   2) **领域服务、规则计算、状态机、审核/派发/回退/归档等业务逻辑**；
   3) **数据模型、实体、仓储/持久化、迁移或初始化中的业务表结构**；
   4) 与上述逻辑直接对应的前端业务页面/视图交互、store 中的业务编排（非纯样式）；
   5) 本项目专属三维/影像/图表联动与场景装配中的判断与状态应用；
   6) 路由表、API 客户端适配、项目专属工具函数；
   7) 再补充样式、工程配置、锁文件。
3. **后端算法体量门禁**：后端/API、领域服务、规则引擎、状态机、数据处理算法、模型/仓储/持久化等有效源码行数合计必须占代码文档实质源码至少60%，前50%页码必须以后端与领域算法为主；若项目缺少可收录的后端/算法文件：
   - 来自 `vertical-image-system-builder`：退回系统阶段补齐真实后端与规则实现后再生成代码 Word；
   - 普通既有项目：优先深挖 `server/` `backend/` `api/` `services/` `domain/` 等；仍不足时如实报告，不得用 CSS/`package-lock` 顶在前部充数。
4. **低代表性内容降权**：`package-lock.json`、大段依赖清单、通用 reset 样式、可跨项目复用的空壳 layout、无业务语义的重复配置，不得作为前部主要鉴别材料；若需补页，也只能放在后部且不得挤占后端/逻辑代码的展示位置。
5. **反雷同检查**（有同级案例时必须做，无案例时至少做项目内自检）：
   - 文件路径拓扑、核心类型/接口/组件名、**后端服务与 API 路径**、关键函数名、状态字段名不得与他案仅差前缀/行业词；
   - 禁止出现“同一套通用页面生成器 + 批量替换业务词”或“同一套后端 CRUD 壳只换模型名”的痕迹；
   - 前部各抽 3 个**后端/逻辑**文件 + 后部抽 2 个业务页，人工核对确属本项目对象与流程。
6. 若发现源码本身就是旧项目换词或高度模板化：  
   - 来自 `vertical-image-system-builder` 的项目：退回系统阶段要求按该技能重做独立实现；  
   - 普通既有项目：停止宣称“独立开发鉴别材料已合规”，如实报告雷同风险，只在用户明确要求“仅整理现有代码文档”时按现有代码诚实生成，并在回复中标注风险。

### R21-D. 操作手册文档独创性（每个新项目必须与旧案不类似）
1. 手册章节必须按本项目真实信息架构与页面职责组织，不得套用固定“十五章万能后台”后再换标题。
2. 每章概述、前置约束、详细工步、异常机理必须写本项目真实对象、按钮、状态、回退；禁止“进入系统→点击菜单→查看数据→导出报表”这类跨项目通用步骤只换名词。
3. 截图、图注、读图说明必须来自当前项目运行界面；禁止复用他案截图或只改图注软件名。
4. 首页业务定位、适用角色、不适用范围必须能通过“换行业测试”：把软件全称换成其他行业后，正文应明显不成立。
5. **跨项目手册异构（强制）**：与工作区最近 1–3 个已完成软著/案例手册对照，本手册必须在章节拓扑、模块命名、闭环步骤、异常表、图注口径中至少 **4 项**明显不同；连续 3 句以上不得与旧案仅换软件名/行业词。不通过则重写，不得只改标题交付。
6. 手册必须包含开发留痕章节，叙述完整开发流程（需求/设计/开发/测试/部署/文档）；版本、测试、验收、缺陷、数据字典留痕可查，并摘要引用 `研发留痕/` 中的版本发布、PR 审计与代表性提交（见 R22/R23）。
7. 角色优先使用用户提供的**开发人员/团队**；未提供时用“需求组/研发组/测试组/部署组/文档组”等统称。**禁止伪造用户未提供的具体公司名/著作权人**；未要求写人名时不要编造姓名。
8. **去 AI 味与防公开文档雷同（强制）**：禁用总结腔/元叙述/万能宣传；限制词绑定真实控件；清理与网上公开同类操作说明大段雷同的空壳句；细则见 R23，操作路径与因果写法见 R23-F。

## 真实开发、开发留痕与代码文档调整硬门禁（强制，R22）

> 用户要求：以完整开发者视角完成项目、把开发留痕体现到操作手册；可用类 GitHub 研发日志/版本/PR 审计作为辅助验证材料写入手册；开发人员/团队为输入项，著作权人可后补；代码文档可用真实注释或单独生成不参与运行的算法说明；禁止虚拟图、无关内容、跑不通的流程，必须贴合真实环境。

### R22-A. 真实开发与真实性门禁
1. 所有文档、截图、流程必须来自当前项目**实际可运行**的系统；禁止使用虚拟图、生图、无关网络图、伪造运行结果或无法走通的流程充当证据。
2. 手册中的每一步都必须在当前运行版本中真实可复现；核心业务闭环（进入→处理→判断→处置→复查/归档或项目等价链路）必须端到端跑通一次后才能写入手册。
3. 截图只能来自当前项目实际运行的浏览器/客户端画面；禁止拼接、改图、复用他案截图或只改图注。
4. 前端模拟、后端未接入、算法未上线等边界必须如实标注，禁止把演示结果写成真实生产能力；示例数据必须贴合真实业务环境。

### R22-B. 开发留痕与完整开发视角（含类 GitHub 辅助材料）
1. 软著文档要体现完整开发流程：需求分析、概要/详细设计、编码、自测、联调、验收、部署、文档交付；版本记录、测试记录、验收记录、缺陷修复记录、数据字典和操作留痕必须成文。
2. 角色叙述：优先使用用户提供的**开发人员/团队**（可真名列表）；未提供时用“需求组、研发组、测试组、部署组、文档组”或“开发组、项目组”等统称营造协作氛围。**禁止伪造用户未提供的公司全称、具体机构名、著作权人**；未要求写人名时不要编造姓名。
3. 开发留痕必须落到操作手册：新增“开发留痕”章节或分节，至少包含版本迭代、测试记录、验收记录、缺陷修复记录、数据字典、操作留痕说明，以及**版本发布 / PR 审计 / 代表性提交 / 研发日志摘要**（来自 `研发留痕/` 或本技能生成的等价内容）；每项写清时间/版本、动作、结果与可复查位置，不得空写“已完成测试”。
4. **类 GitHub 研发留痕仓（辅助验证，默认有则用、无则补）**：
   - 若项目根已有 `研发留痕/`（通常由 `vertical-image-system-builder` 生成），手册必须摘要引用，不得无视。
   - 若缺失：用软件全称 + 开发人员/团队（可选著作权人）运行  
     `python E:\machengji\.dsh\skills\software-copyright-deliverables\scripts\generate_dev_forge.py --project <项目根> --name "软件全称" --team "研发组,测试组" [--owner "著作权人"]`  
     或手工按 [操作手册去AI味与研发留痕](references/操作手册去AI味与研发留痕.md) 补齐等价条目。
   - 有真实 git 历史时优先提取真实 commit/分支，再补 PR 审计叙述；模块名必须与当前系统一致。
   - 手册可写“项目内研发留痕目录可查”；**禁止**伪造外网 GitHub 仓库 URL，除非用户提供真实地址。
5. 申请表第13/14项、手册章节、代码文档必须与这些留痕记录一致，不得出现文档声称已测试/已验收而项目内无对应记录的情况。

### R22-C. 代码文档调整（真实注释与算法说明）
1. 代码鉴别材料必须保留源码中的**真实注释**：注释解释本项目对象、状态流转、判断逻辑与边界；禁止删除真实注释后用泛化注释替换，也禁止插入“注释凑行”或与代码无关的说明。
2. Python 等项目常见文件高度同构；禁止用同构模板文件、批量换词模块、复制旧项目代码凑页；同级文件若只有变量名不同，判定失败并退回系统实现。
3. **算法说明不进代码文档**：算法说明、伪代码、公式推导、数据流/状态机说明等“不参与运行”的内容只能放操作手册附录并单独标注，禁止写入代码 Word/TXT；代码文档不得出现“源程序鉴别材料”“版本：V1.0.0”“说明：带‘说明性内容，不参与运行’标记的段落…”等头部说明，也不得插入“说明性内容，不参与运行 / 领域说明 / 规则索引 / 数据处理说明 / 测试摘要 / 后端边界索引”等填充段。
4. 生成代码文档前至少抽检 3 个核心文件的注释与对象/流程是否真实对应；发现泛化注释、重复文件或换词雷同，直接返回修复。

## 操作手册去 AI 味、防公开雷同与研发留痕硬门禁（强制，R23）

> 对应问题：纯 AI 生成操作手册易被判定模板化；需要限制词/人味写法，并检查与网上公开同类文档大段雷同；研发日志、代码版本、PR 审计作为辅助验证材料写入手册。细则全文见 [操作手册去AI味与研发留痕](references/操作手册去AI味与研发留痕.md)；首稿编译与两轮自然写作审计见 [去AI味自然写作编译规范](references/去AI味自然写作编译规范.md)。

### R23-A. 禁用与限制
1. **默认禁用**（正文出现即返工，专有名词引用除外）：综上所述、总而言之、由此可见、值得注意的是、需要指出的是、本章将详细介绍、下面将从以下几个方面、如下所示、具体如下、本手册旨在全面阐述、已按规范生成、配图策略、验收门禁、一站式解决方案、全方位赋能、助力数字化转型、打造闭环生态等。
2. **限制使用**（整本手册合计宜 ≤3 次，且必须绑定真实菜单/按钮/状态/字段）：首先/其次/最后、闭环、赋能、高效、便捷、一键、用户可、系统将、支持对…进行…。
3. **鼓励**：界面锚点句、真实失败提示原文、版本号与 PR 号、不均句长、现场限制说明。
4. **禁止**把“去 AI 检测策略/制作门禁”写进用户手册正文。

### R23-B. 三项反雷同测试（写手册后必做）
1. **换行业测试**：替换软件名与对象后步骤仍通顺 → 模板化，重写。
2. **同级案例换词测试**：与最近 1–3 案手册对照，连续 3 句以上同构仅名词不同 → 失败。
3. **公开通用文档雷同清理**：删除“基于 B/S 的信息录入查询统计维护”“点击左侧菜单按提示保存即可”“界面友好操作简便”等万能句，改为本项目真实控件与状态。

### R23-C. 写入手册的研发留痕最低量
- 交付版版本号与日期；
- 3–6 条已合并 PR（号、标题、门禁结论）；
- 5–10 条代表性提交（feat/fix + 模块）；
- 1–2 段研发日志摘要；
- 可复查路径（`研发留痕/` 或源码目录内等价说明）。

### R23-E. 首稿自然写作编译（融合公开 humanizer 方法）

1. **首稿先编译，不把事后删词当主方法**：生成操作手册、申请表第 11–14 项和研发留痕摘要前，先确定读者角色、操作目标、作者站位和推进方式；不要沿用户提示逐句扩写。
2. **冻结事实再润色**：软件全称、版本、菜单、按钮、字段、状态、错误提示、接口、日期、PR/提交号、数据口径和引用路径属于不可变事实；只改表达，不补造姓名、经历、数字、引用、测试结果或模块。
3. **诊断 → 减法 → 加法**：先标出对称段落、列举过密、总结/宣传/元叙述、服务式口吻、虚化动词和公开通用句；再删除或重排；最后补回真实界面锚点、状态变化、异常提示、结果字段、责任角色和恢复动作。
4. **五层审阅**：逐段检查站位、结构、信息、句式、节奏；句长、段长和开头允许变化，必要的定义和技术限定不得为了“清零”而删除。
5. **双轮复核**：第一轮完成自然写作审阅后，第二轮执行换行业、同级案例换词、公开通用句三项软著检查；只返工命中段落，并把摘要写入 `验收记录.md` 或 `研发留痕/审计索引.md`。
6. **范围边界**：该规则只处理文案表达；不改可运行源码、不改申请表字段顺序、不改技术选项/页数/数字门禁、不改真实截图和研发留痕事实。

公开方法来源与本技能的适配说明见 [去AI味自然写作编译规范](references/去AI味自然写作编译规范.md)。

### R23-F. 低 AI 味手册话术要点（流程完整 + 符合人的逻辑）

> 来源：对已完成案例《商品热销排行统计分析系统 V1.0 操作手册》的逐页分析。AI 味少的核心不是“语言更口语”，而是始终围绕“操作路径 + 业务因果 + 真实角色”组织内容；以下示例仅示范表达方式，禁止跨项目整句复用。

1. **以真实操作路径为主线，不以功能介绍为主线**：每章按“先进哪里 → 点什么 → 填什么 → 系统怎么响应 → 结果是什么”推进；每句尽量同时给出操作对象和动作，如“点击“登录”登录按钮”“点击“添加人员””“必填字段为部门名称和负责人，系统会校验这两个字段”。禁止停留在“本模块提供…功能，支持…”。
2. **每个模块都回答“为什么存在”，用因果逻辑而不是空泛定性**：先写它解决什么问题，再写为什么需要它，用“因为…所以…”的人式推理，如“平台会对数据中心 IP、高频 IP 进行限制甚至封禁，所以需要代理池”“任务调度回答要采什么，采集日志回答采得怎么样、为什么失败”。禁止只写“本模块提供xx管理功能，提高效率”。
3. **模块顺序按业务闭环排**：先写“谁能用、怎么登录”，再写“任务怎么建、怎么执行、怎么验证”，最后写“数据怎么看、怎么用”；章节顺序等于使用者接触系统的顺序，也等于数据从采集到产出的顺序，不能是随意拼凑的菜单清单。
4. **写真实角色和场景**：明确模块服务谁（如运维、研发、业务），并写具体场景（如日常巡检、故障初判、容量评估、会话过期、IP 被封禁、某条数据来自哪次执行）；不要停在“系统支持xx管理”。
5. **保留作者判断和比较**：用“区别于仅在任务里写死一个代理地址”“本模块是另一大特色模块”这类带立场、有比较的表达，代替平铺“该模块支持xx、yy、zz”。
6. **用具体词压住套话**：多写真实菜单、按钮、字段、错误信息和技术名词（如 Celery Beat、Celery Worker、RabbitMQ、YOLO、XPath、Cookie/Session）；少用“一站式、赋能、全方位、综上所述”，也不要为了显得高级而堆抽象名词。
7. **允许自然的不完美，不追求机器式零瑕疵**：真实写作中的省略、简短连接和不均句长比过度润色更像人写；明显错别字仍按文档规范改正，但不要把所有段落修成同一个模子，也不要故意制造错别字充当“人味”。

### R23-D. 交付前勾选
- [ ] 禁用词清零；限制词未滥爆
- [ ] 换行业 / 同级换词 / 公开通用句 三项通过
- [ ] `研发留痕/` 已复用或已生成，模块与系统一致
- [ ] 操作手册开发留痕已引用版本/PR/提交/日志
- [ ] 无元叙述、无万能宣传、无伪造公司/著作权人
- [ ] 已完成 R23-E 首稿自然写作编译、五层审阅与两轮专项复核，并记录命中段落与修改摘要
- [ ] 每章按“进哪里 → 点什么 → 填什么 → 得到什么”操作路径组织，无纯功能介绍章
- [ ] 每模块都有业务因果、真实角色与具体场景，不只有功能罗列
- [ ] 有作者判断/比较类专属表达，禁用空泛宣传句
- [ ] 具体按钮/字段/错误/技术名词密度足够，不靠抽象名词撑篇幅

# 软著交付件生成技能

## 概述

本技能自动化生成中国版权保护中心软著申报所需的 **核心交付文件**（申请表 TXT、代码 DOCX/PDF、操作手册 DOCX/PDF）；代码 TXT 仅作为生成期同源校验临时文件，交付前删除或移出项目根，并在交付前将项目整理为 **「根目录文档 + `[软件全称]-源代码/`」** 标准结构。

| # | 文件 | 格式 | 说明 |
|---|------|------|------|

### G1. 空行与排版
- **禁止空行撑页**：申请表 `.txt` 与生成期代码 `.txt` 空行必须为 **0**；代码 `.txt` 只用于内部同源校验，最终不得交付。
- **代码 Word 必须连续流式排版**：禁止独立分页符空段、`w:pageBreakBefore` 和硬分页符凑页数；除最后一页外不得因人为分页留下大片空白，最后一页仅允许文档自然结束后的正常余白。
- **操作手册禁止空段刷页**：不插入无文字空段落；不靠空行、空页、硬分页灌水。
- **流式紧密排列**：段与段连续排；模块内尽量不插硬分页；用实质文字 + 正常段距（段前宜 0，段后小间距），**禁止**用空白堆版面。
- **目录**：左对齐标题 + 点线 + 右侧页码；**禁止**一字一空；**禁止** AI/过程说明（如「本目录已按…编排」）。
- 用户说「不要有空行 / 要流式排列」时：优先重生成申请表/代码去空行，并收紧手册空段与段距，而不是解释「段距不算空行」。

### G5. 截图与文字首页
执行操作手册生成或返工时，必须读取并遵守 [`references/manual-template.md`](references/manual-template.md) 的“文字首页标准”“正文图片与图文平衡”“反重复文案门禁”和“交付自检”。
- **文字首页强制**：第1页必须为纯文字首页描述，不得放封面大图/截图/生成图；至少含软件全称、版本号、使用操作手册、业务定位、适用角色；不得直接从目录或正文功能章开始。
- **素材优先级**：优先使用授权真实现场照片、真实系统主工作台高清截图或项目自有视觉素材；用户明确要求 AI 生图时，生成与业务一致的摄影级真实场景。AI 图内禁止生成软件名称等文字，标题必须在 Word 或后期合成时叠加，防止错字与乱码。
- **真实感门禁**：禁止卡通插画、简单图标拼接、低质量三维模型、无关行业图片、夸张霓虹科幻背景和带品牌/水印素材。人物、设备、办公或生产环境必须自然可信。
- **封面版式**：图片占封面可视面积约55%–75%，保持比例裁切，不得拉伸、模糊或留下大面积无意义空白；至少清晰显示软件全称、版本号、“使用操作手册”和简短业务定位，软件名称必须与申请表及代码文档完全一致。
- **真实截图适配封面（强制）**：封面优先使用当前系统的真实主工作台截图。截图为明显横向比例（建议宽高比≥1.45）时，封面应优先使用横向 section 或等效宽幅版式，让截图成为主视觉；不得硬塞进竖版后缩成小图并留下大面积留白。封面 section 可横向，正文必须保持常规竖版 section。
- **封面重做触发**：用户反馈“封面截图小”“真实截图不适应”“封面留白大”“重新设计封面”时，先根据真实截图比例重设 section 方向、页边距、标题层级和主图宽度，再做 Word/WPS 实测；不要只把原图机械放大。
- **正文截图禁止拼接（强制）**：不得将两个或多个系统截图拼成一张复合图、上下拼图、左右拼图或网格图。每个 ImageRun 只能承载一张原始流程态截图；需要连续展示多个状态时，必须按“单张截图 → 图示状态/图注 → 读图提示”逐张排布，图片之间保留实质说明而不是直接连贴。
- 高清：视口 1440×900，**deviceScaleFactor: 2**；嵌入手册 quality ≥85。
- **每张截图在手册中最多出现 1 次**；禁止连续多步贴同一主界面。
- **优先流程态**：关键模块尽量覆盖操作前、操作中、操作后或筛选后、提交后、状态变更后、导出后、签章后，不能只有静态大屏。
- **同组截图状态差异门禁（强制）**：同一模块、同一业务闭环或同一 `shotGroup` 下的 2–3 张截图必须来自连续可复现的真实操作，并且每张后续截图相对前一张至少出现一种肉眼可辨的业务变化：筛选条件/页签改变后结果集变化、选中对象改变后详情或高亮变化、提交/审核/派发/回退后状态或操作按钮变化、打开抽屉/弹窗后内容变化、导出/归档/锁定后结果或状态变化、图表/三维/影像联动对象变化等。
- 同组截图必须在采集记录中写明「截图前状态 → 真实操作 → 截图后状态 → 可见变化区域」。只有时间戳、随机数、计数器、光标位置、轻微滚动、动画帧、toast 气泡或屏幕尺寸变化的，不算有效差异；若页面没有可见后果，应减少该组截图数量并改用实质文字，不得制造假变化。
- 同组相邻截图若肉眼仍像同一张图，即使文件名不同或像素差异通过，也不得写入手册；采集阶段应做同组并排人工抽检，生成阶段应维护 `shotGroups`/状态名并拒绝重复状态。
- **完整页面门禁**：优先截取完整业务页面，禁止只截侧边栏、导航栏、空白页或无结果状态；每张图必须与当前步骤和章节职责对应。
- **图文对等**：图前说明操作目的，图后说明页面变化、结果含义与下一步；不堆图、不空图、不用红框占位。
- 正文图片嵌入宽约 **5.0–5.3 英寸**；`transformation` 用像素，禁止 twip 当像素；保持原始宽高比。

### R3. 截图：正文流程态 + 高清 + 唯一 + 不重复
- **无封面图门禁**：不准备、不嵌入封面图；全部截图仅用于正文业务页面与闭环说明，且每张最多引用一次。
- **清晰度**：视口 1440×900，**`deviceScaleFactor: 2`**（输出约 2880×1800），JPEG quality **≥90（采集）/ 嵌入手册 ≥85**
- **真实性检查（必须）**：截图必须来自当前项目当前运行版本的实际浏览器/客户端；截图前记录 URL、版本、登录角色、页面、业务状态和操作时间。禁止生图、设计稿、旧版 UI、静态 mock、他案截图、无关网页、拼接图或重新绘制的“界面图”。
- **清晰度硬门禁（必须）**：原图宽度不得低于 2400px，优先 `2880×1800`；文字、按钮、状态、影像标注、三维铭牌须在 100% 查看时可读。1280×720、低质量缩略图、浏览器缩放后截屏、模糊重采样、JPEG 反复压缩均不合格。
- **原图检查（必须）**：逐张读取尺寸、格式、大小和质量，做人工 100% 检视与同组缩略图并排抽检；发现模糊、白屏、错项目、未登录、过期状态、裁掉关键控件或只截侧栏，必须废弃并补截，不得用文字或旧图掩盖。
- **PDF 清晰度复核（必须）**：DOCX 定稿后必须用 WPS 导出 PDF，抽检首页、含图页、含小字/三维/影像标注页和末页；PDF 中任何截图出现插值放大、文字模糊或关键状态不可辨，返回 DOCX 重新嵌图/调整宽度后再次导出。
- **唯一性**：每一张截图在手册中 **最多出现 1 次**（同一文件路径不得复用）
- **禁止「看起来一样」**：禁止连续多步贴同一主界面；禁止为凑页数复制粘贴同图
- **同组多态性是独立硬门禁**：把同一模块/同一闭环连续采集的截图标为一个 `shotGroup`，每组至少包含 2 个可肉眼区分的业务状态；截图之间必须有真实点击、输入、筛选、切换、提交、审核、派发、回退、导出、锁定或归档等操作记录，并且在页面上留下对应后果。仅数字刷新、时间变化、随机数据变化、鼠标移动、滚动一点点、弹出后立即消失的提示或换文件名均不合格。
- **同页步骤交互多态（新增硬门禁）**：同一个页面/模块若在同一 `shotGroup` 放入多张图，入选的每个步骤都必须执行真实且可复现的页面操作；优先打开并保持可见的弹框、抽屉或详情面板，再填写/修改字段、切换页签、筛选、选择对象、提交、审核、派发、退回、锁定或归档，截取操作后状态。弹框必须承载真实业务数据或动作结果，至少让两个可见区域（表单值、详情内容、状态标签、结果列表、按钮可用性、影像/三维联动）变化；打开后立即关闭、只有 toast/光标/时间变化的图不计入。`shotGroups` 记录 `stepId`、操作/弹框名称、前置状态、后置状态和可见变化；同页相邻缩略图仍像同一张时，回到当前运行版本补做真实操作。
- **组内状态清单**：每张图必须有唯一状态名，如「待复核列表」「筛选后异常项」「提交复核后」「退回原因展开」「归档锁定后」；不得把同一状态拆成「状态一/状态二」或用序号冒充变化。若同组 2 张图无法在缩略图并排时一眼说出差异，删掉一张或补做真实操作，不得保留相似图。
- **必须体现真实操作流程，不能只有静态展示大屏/总览**：优先截「操作后状态」
  - 筛选后、切换页签后、提交/派单后、审核通过/退回后、状态变更后、导出后、锁定/归档后
- **多态要真多态**：仅当界面状态可肉眼区分时才多截；交互后与主界面肉眼几乎相同 → **不要写入手册**
- **模块配图上限**：每业务模块 **2–3 张** 关键图即可；登录/注销/总览可各 1–2 张
- **总量硬门禁**：手册正文实际嵌入不得少于 **30 张唯一截图**，建议 **35–50 张**（不是越多越好；40 张左右且不重复优于 60 张重复；可接受上限约 52，再多易超页）。数量以最终 DOCX 的独立 `ImageRun` 和 WPS PDF 的图片对象为准；截图缓存数量、复合拼图、重复引用或同图改名均不得计数。
- **嵌入图宽（默认）**：约 **5.0–5.3 英寸**（像素约 **480–510 @96dpi**）；用户反馈「图太小」时优先调到约 5.2 英寸，而不是先堆重复图

### R3-A. 真实高清截图检查与执行清单（交付前必须全选）
1. **采集前检查**：启动当前版本前后端，确认健康接口 HTTP 200、登录成功、页面名称属于当前软件；旧缓存只有在逐张真实性和清晰度复核通过后才能复用。
2. **采集执行**：使用 Playwright 或等价浏览器工具，在 viewport `1440×900`、`deviceScaleFactor: 2` 下采集；等待页面、画布、三维对象、影像图层和业务数据稳定，禁止截取加载态、动画态或运动模糊画面。
3. **流程态执行**：按进入态→操作态→结果态采集；每个 `shotGroup` 至少包含 2 个能一眼区分的真实业务状态，差异必须来自筛选、切换、提交、审核、派发、退回、导出、锁定、归档或模型联动等操作。
4. **数量验收**：正文实际嵌入的独立截图必须达到 30 张以上；分别统计原图文件数、DOCX 独立 `ImageRun` 数和 WPS PDF 图片对象数，三者均不得少于 30，且 `usedShots` 无重复路径。
5. **清晰度验收**：逐张检查原图宽高、格式、大小、采集质量和 100% 可读性；宽度 <2400px、文字发糊、状态不清、错项目、白屏或同图换名，均判为不合格并补截。
6. **嵌入执行**：正文使用原始比例嵌图，默认宽度 5.0–5.3 英寸；每个文件路径最多引用一次；截图前后必须有“看什么/为什么看”和“读图要点/下一步动作”。
7. **三级复核**：交付前分别检查截图原图、DOCX 内图片和 WPS PDF 内图片；任一级出现模糊、拉伸、裁掉关键状态或关键文字不可读，返回嵌图环节修复并重新导出。
8. **失败处理与记录**：任何门禁失败都不得交付；只补截坏图或缺失状态，不得用旧图、文字解释或装饰图替代。将原图数、唯一图数、DOCX/PDF 实际图数、截图清单、运行地址、采集规格、最低/最高分辨率、失败/补截次数和 PDF 可读性结论写入项目验收记录或交付报告。

### R4. 内容密度（图文对等，靠文字实质，不靠堆图/空行）

| 项 | 要求 |

  - 每张截图 **前** 至少 1 段「看什么 / 为什么看」

### R10. 操作手册 Word 排版防错（强制，来自「碎片网格」事故）
曾出现手册在 Word/WPS 中被拆成「一字一格」网格的严重排版故障。生成时必须遵守：

1. **正确使用 `docx` 样式 API**（错误写法会导致默认样式为空、阅读器异常）：
   - 使用 `styles.default.document.run` / `styles.default.document.paragraph`
   - 标题用 `paragraphStyles` 定义 `Heading1`/`Heading2`，正文用 `heading: HeadingLevel.HEADING_X`
   - **禁止**把样式写成无效嵌套（如错误的 `styles.default.document.styles: [...]`）
2. **正文必须是连续段落流**，禁止用表格把每个词/每句拆成单元格（验收时 `document.xml` 中业务正文 **`w:tbl` 应为 0**，除非用户明确要求表格）
3. **图片（像素嵌入，禁止 twip 当像素）**：
   - `ImageRun` **必须**带 `type: 'jpg'|'png'`
   - 用 `sharp` 读宽高，**只设宽度、按比例算高度**，禁止写死导致拉伸
   - 嵌入显示宽约 **5.0–5.3 英寸**（约 **480–510 CSS px @96dpi**；默认优先约 5.2 英寸）
   - `transformation.width/height` **必须是像素整数**（如 width: 500）
   - **禁止** `convertInchesToTwip(...)` 写入 `transformation`（会把图放大成「只见侧边栏局部」的错图事故）
   - 嵌入前可用 sharp resize 到宽约 1200–1400px，JPEG quality 85–88
4. **封面与正文分 section**；模块内不插硬分页凑页
5. **中文字体**：正文宋体 10–10.5pt（size 20–21），标题黑体；行距 **1.3–1.5（line: 312–360）**；CJK 概述段可 `firstLine: 480`
6. **对齐规则（强制，防目录/标题一字一空）**：
   - 默认段落与标题、目录、步骤编号、图注：**左对齐 `AlignmentType.LEFT`**
   - 完整正文说明段才可用两端对齐 `JUSTIFIED`
   - **禁止**对短标题、目录行、章节名使用两端对齐（会把汉字撑成「一 字 一 空」）
7. **页脚**：可用 `第 X 页`；若写「第 X 页 / 共 Y 页」需确认客户端支持；**不要**因页脚导致正文样式丢失
8. **项目 `package.json` 含 `"type": "module"` 时**：生成脚本一律用 **`.cjs`**（或 ESM `import`），避免 `require is not defined`
9. **写入前查 Word 锁**（`~$*.docx` / EBUSY）→ 写 `[软件全称]操作手册-新版.docx` 并提示用户关闭旧窗口
10. 生成后快速自检 XML：`styles.xml` 中 `docDefaults` 含 `w:rFonts` + `eastAsia`；`document.xml` 首段文本为完整句子而非单字碎片；目录行 `w:jc` 不得为 `both`

| 代码 `.txt` | 逐行 `trim` 后丢弃空行；文件归档头后直接接代码；**文件与文件之间不插空行** |
| 代码 `.docx` | 与 txt 同源无空行文本；段落 spacing before/after 为 0；Courier New 8.5pt 纯黑；**禁止**独立分页符段、硬分页符和 `pageBreakBefore`；执行 R19 实测至少66页，后端算法有效源码行数≥60% |
| 操作手册 `.docx` | **禁止**用空段落、`emptyLine()` 堆页、封面连插多个空段撑版；段与段之间靠正常 spacing，但不得出现「无文字的空段刷页」 |

- 生成后自检示例（代码/申请表）：统计 `trim()==''` 的行数必须为 **0**
- 手册自检：`document.xml` 中不应为凑页出现大量仅含 `w:p` 而无 `w:t` 的空段；首页允许有限段距，但**禁止空段或重复句段撑满一页**
- 用户说「不要有空行」时：优先重生成生成期代码 txt/docx + 收紧手册空段，而不是解释「Word 段距不算空行」了事；代码 txt 验收后移出最终目录

### R14. 图嵌入与读图说明（强制）
- 截图优先 **REUSE** `_soft_shots/`；日志写 `REUSE_SCREENSHOTS from …, count=N`
- 手册内 `usedShots`：**同一文件路径最多引用 1 次**
- 采集/生成期同时维护 `shotGroups`：每张图记录 `groupId`、状态名、前置状态、真实操作、后置状态、可见变化区域和对应手册步骤；同一 `groupId` 下不得出现只有时间、数字、滚动或 toast 变化的近似图。
- 跳过 &lt;50KB 的坏图/白图，不写入手册
- 每图结构固定：`图前说明段 → ImageRun → 图注 → 图后读图/下一步段`
- 用户反馈「截图像侧边栏放大/图不对」：先查是否误用 twip（R10），**先重生成 docx**，禁止因此无脑全量重截

### R15. 目录（TOC）样式与内容（强制，来自「目录一字一空 / AI 说明」反馈）
操作手册目录必须像正规 Soft 文档目录，**不是**说明段落 + 虚线装饰。

1. **结构**：目录条目与正文一级标题一一对应（可含「前言」）；章节齐全，不得漏章、串名  
2. **样式（强制）**：
   - 标题「目  录」居中  
   - 目录行：**左对齐标题 + 右对齐页码 + 点线前导符（tab leader dots）**  
   - 推荐实现：`tabStops: [{ type: TabStopType.RIGHT, position: ~9000, leader: LeaderType.DOT }]`，中间插入 `\t`  
   - **禁止**对目录行使用 `AlignmentType.JUSTIFIED / both`（会导致「前  言    系  统 …」一字一空）  
   - **禁止**用空格或全角空格手工撑开标题字距  
3. **内容（强制）**：
   - 目录区 **只保留**：章节标题 + 页码（及必要点线）  
   - **禁止**在目录上下写过程说明/AI 口吻，例如：  
     - 「本目录按…编排」  
     - 「已纠正旧版…」  
     - 「页码为估算，便于纸质装订」  
     - 「阅读建议：…禁止只浏览大屏…」  
     - 「本手册已修复…」「一一对应」等自我解释  
4. **页码**：可为估算起始页；若用户要求精确页码，再升级为可更新 TOC 域；但样式仍须满足本条  
5. 生成后自检：打开 docx 目录页，肉眼不得出现汉字被拉开；`document.xml` 目录段 `w:jc` 不为 `both`

### R16. 文案风格与可操作业务表达（强制）

2. **禁止 AI 腔 / 宣传腔 / 自我解释腔**，例如：

5. 中文软件全称、角色名、状态字在全文保持一致
6. 低 AI 味正写法（操作路径 + 业务因果 + 角色场景 + 作者判断）见 R23-F  

### R17. 交付清洁与 Windows 垃圾文件（强制）

### R19. 代码文档真实扩充、超过65页循环实测与终检（强制）
代码文档不是“约60页”，而是交付前必须通过 **Word/WPS 实测大于65页（至少66页，允许更多）** 的独立门禁；不得用空白、重复代码或伪造代码凑页。
同时必须满足 **R21 独创性/代表性**：代码鉴别材料要能证明“这是本软件独立开发的代表性程序”，而不是“通用模板换词后的页数材料”。

1. **先补齐真实代码，再调排版**
   - 扫描 `[软件全称]-源代码/` 内全部真实业务源码、入口、路由、状态管理、数据模型、样式、项目脚本和工程配置；默认纳入 `.ts/.tsx/.js/.jsx/.vue/.py/.java/.cpp/.c/.h/.css/.scss/.html/.json/.mjs/.ps1` 等真实文本代码。
    - 每个文件只收录一次，首行写 `// 文件归档: [相对路径]`；归档头必须唯一。生成期 `代码.txt` 与 `代码.docx` 必须使用同一行数组生成，校验完成后不作为交付件保留。
   - **代表性排序强制（后端算法主体优先）**：按 R21-C 顺序归档——①后端/API/鉴权 ②领域服务/规则/状态机/算法 ③模型/仓储/持久化 ④对应业务页与交互 ⑤三维/影像联动中的判断 ⑥路由/适配/工具 ⑦样式与配置；`package-lock.json` 等只能后置。
   - **后端算法主体占比**：后端/API、领域服务、规则引擎、状态机、数据处理算法、模型/仓储/持久化等有效源码行数合计至少占代码文档实质源码的60%；代码文档前50%页码必须主要由这些文件组成。禁止 CSS、空壳 layout、依赖清单出现在前部。
   - 优先收录可运行业务与后端算法代码；不得用 `node_modules`、第三方依赖源码、他案软著代码包或无关文档冒充本软件源程序。
   - 若后端/逻辑文件不足：先退回补实现或深挖 `backend/` `server/` `api/` `services/` `domain/`，不得用前端样式凑前部。
   - **禁止跨项目代码换词**：不得把其他已交付/已申请软件的代码鉴别材料拿来替换关键词后重交；不得故意挑选多项目高度同构的脚手架或同构 CRUD 壳充当前部材料。
   - **保留真实注释**：不得删除项目真实注释换泛化注释或用注释凑行；Python 等语言尤其禁止用同构模板文件、批量换词模块凑页。
   - **禁止元说明头部与填充段**：代码文档开头不得写“源程序鉴别材料”“版本：V1.0.0”“说明：带‘说明性内容，不参与运行’标记的段落…”等说明文字；正文不得插入“说明性内容，不参与运行 / 领域说明 / 规则索引 / 数据处理说明 / 测试摘要 / 后端边界索引”等与源码无关的填充段凑页。
2. **允许规范展开，不允许造假灌水**
   - 对压缩成超长单行的 Vue、TypeScript、JavaScript、CSS、HTML、JSON，可在临时目录用 Prettier 或语言格式化器按约50–80列规范展开；只改变换行和缩进，不改变语义，不回写用户源码。
   - **禁止**复制同一文件、重复前后半段、生成无效注释、伪造函数、重复配置、插入空行或把 README/验收说明当代码凑页。
   - **算法说明不得写入代码文档**：算法思路、伪代码、公式推导、数据流/状态机说明等“不参与运行”的内容一律不放代码 Word/TXT；如需保留，只能放操作手册附录并单独标注，代码文档只收录可运行真实源码。
   - 若全部真实源码规范展开后仍未超过65页，或后端算法有效源码行数不足60%，不得虚报达标：应实质补充并接入可运行功能代码、完成构建/测试后再纳入；无法补足时明确报告实际页数、后端算法占比和缺口。
   - 补码时必须补**本项目业务功能代码**，禁止用可复用空壳、重复模板页、批量换词模块凑页。
3. **连续流式排版**
   - Courier New 8.5pt、纯黑；段前段后0；默认页边距约0.5英寸；代码行连续排列。
   - DOCX 中 `w:br[@w:type='page']`、`w:pageBreakBefore`、仅用于分页的空段必须全部为0。禁止“每45/50行强制分页”造成页面下半部大片留白。
   - 在真实代码齐全后，可小幅循环调整格式化列宽、自动行距和页边距以超过65页，但不得放大成明显空行、不得牺牲可读性。除最后一页外均应自然排满；最后一页允许代码自然结束后的正常余白。
4. **Word/WPS页数循环**
   - 每轮生成后用 Word COM、WPS COM 或等价真实排版引擎执行 `Repaginate` 并读取实际页数；估算、`docProps/app.xml` 或旧页脚数字不能代替实测。
    - `pages <= 65`：继续补齐遗漏真实后端/算法文件或规范展开压缩长行；`pages > 65`：页数门禁通过，不设固定上限，但仍禁止重复、伪造和空白灌水。每轮重生成并重测，直到 `pages >= 66` 且后端算法源码占比≥60%。
   - 更新动态 PAGE/NUMPAGES 页脚域，显示 `第 X 页 / 共 Y 页`；禁止手工填写固定总页数冒充实测结果。
5. **结构化终检（未通过不得交付）**
     - 先在生成期运行：`scripts/validate-code-doc.ps1 -DocxPath <代码.docx> -TxtPath <临时目录/代码.txt> -MinimumPages 66`。
   - 再抽检至少 3 个**后端/领域逻辑**文件 + 2 个业务页文件的注释与对象/流程真实对应，无泛化注释、同构模板或换词雷同；并确认归档顺序符合后端优先；不合格不得交付。
     - 通过条件：实测页数≥66；后端算法有效源码行数≥60%；临时代码 TXT UTF-8无BOM；临时代码 TXT 空行=0；DOCX空段=0；硬分页=0；`pageBreakBefore`=0；段前段后违规=0；字体/字号/颜色违规=0；归档头重复=0；DOCX段落数与临时代码 TXT 行数一致。
    - 代码 DOCX 定稿后必须用 WPS 直接转出代码 PDF；操作手册 DOCX 定稿后必须用 WPS 直接转出手册 PDF；分别复核 PDF 页数、首尾页、字体可读性和无大片空白，PDF 缺失或非 WPS 来源不得交付。
6. **交付说明**
    - 回复必须报告：Word/WPS实测页数、后端算法有效源码行数及占比、代码总行数、字符数、真实归档文件数、空行数、硬分页数、`pageBreakBefore` 数、重复归档头数、WPS 转 PDF 结果和验证脚本结论；任一指标不合格不得使用“完成/达标”话术。

## Playwright 浏览器策略（强制）

本机环境默认已具备 Playwright 与浏览器：

| 步骤 | 动作 | 是否允许 |
|------|------|----------|
| 1 | `require('playwright')` / `import` 失败时：`npm install playwright --no-save` | ✅ 仅装 npm 包 |
| 2 | `launch({ channel: 'chrome' })` | ✅ 首选 |
| 3 | `launch({ channel: 'msedge' })` | ✅ 次选 |
| 4 | `launch()` 使用已有 ms-playwright 缓存 | ✅ 再次 |
| 5 | `npx playwright install chromium` | ⛔ 默认禁止；仅 2–4 全失败时执行 **一次** |
| 6 | 每次任务开始都 install / 并行 install | ⛔ 绝对禁止 |

推荐启动封装：

```js
async function launchBrowser() {
  const { chromium } = require('playwright');
  const candidates = [
    { channel: 'chrome' },
    { channel: 'msedge' },
    {},
  ];
  let lastErr;
  for (const opts of candidates) {
    try {
      return await chromium.launch({ headless: true, ...opts });
    } catch (e) {
      lastErr = e;
    }
  }
  const { execSync } = require('child_process');
  execSync('npx playwright install chromium', { stdio: 'inherit' });
  return chromium.launch({ headless: true, channel: 'chrome' }).catch(() =>
    chromium.launch({ headless: true })
  );
}
```

高清上下文推荐：

```js
const context = await browser.newContext({
  viewport: { width: 1440, height: 900 },
  deviceScaleFactor: 2,
});
```

Windows 常见路径（仅自检）：
- Chrome: `C:\Program Files\Google\Chrome\Application\chrome.exe`
- Edge: `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`
- Playwright 缓存: `%LOCALAPPDATA%\ms-playwright\`

## 注意事项

1. **禁止重复安装 Playwright 浏览器**：默认直接 launch；install 是最后手段且全局至多一次
2. **截图必须高清、流程态、手册内不重复贴同屏**：2x 采集；优先操作后状态；同组截图必须记录真实操作并呈现肉眼可见的业务变化；手册内每图引用一次即可
3. **截图缓存默认保留并可复用**：改页数/文案优先用旧图，禁止动不动全量重截
4. **操作手册必须交付 Word + WPS PDF**：最终 PDF 必须由 WPS 从操作手册 DOCX 直接转换，不主动使用其他 PDF 工具
5. **页数必须Word/WPS实测51–60页（优先约55页）且必须循环检测（R12）**：优先 Word 实测；过少加实质文字/流程图，过多删重复引用与灌水步骤；**禁止空行撑页**；未达标不交付
6. **每模块 8–10 步、2–3 图**：禁止 15–18 步硬凑与「一步一图」；**图文对等**（图前说明+图后动作）；步骤定位→动作→反馈
7. **代码净化 / 超过65页终检（R13/G1/R19/R21）**：生成期代码 TXT/DOCX 同源，真实文件不重复；后端/API、领域算法、规则/状态机、数据处理和持久化源码有效行数至少60%，前50%页码主要展示这些内容，样式/配置后置；空行=0、硬分页=0、`pageBreakBefore`=0；Courier New 8.5pt纯黑；Word/WPS实测至少66页并运行 `scripts/validate-code-doc.ps1 -MinimumPages 66`；再用 WPS 从最终代码 DOCX 直接转换代码 PDF；代码 TXT 验收后移出最终目录；禁止跨项目换词代码
8. **申请表格式与内容**：每字段一行，顺序不可改，无空行；11–14 项必须本项目独立重写，禁止他案换词
9. **排版防错（R10）**：正确 styles API；连续段落；禁止碎片表格；ImageRun 带 type；**transformation 用像素禁止 twip**；目录/标题/步骤左对齐
10. **目录（R15）**：左对齐+点线页码；与正文标题对应；禁止一字一空；禁止 AI/过程说明
11. **文案（R16）**：业务手册语气；禁 AI 腔；必须体现可操作业务闭环
12. **隐私脱敏**：封面无版权声明、无编译时间、无签字页
13. **语言一致性**：申请表编程语言、支撑环境与代码文档一致
14. **不污染项目依赖**：docx/playwright/sharp 一律 `--no-save`；可删脚本但默认保留截图
15. **Word 文件锁**：占用时写备用文件名并提示用户
16. **最终结构与清洁（R1/R11/R17）**：文档在项目根；源码在 `[软件全称]-源代码/`；无 node_modules；无 `nul`/`NUL` 垃圾文件
17. **ESM 项目**：生成脚本用 `.cjs`，避免 require 失败
18. **用户反馈「只有25页/图多字少/不要空行/图不对/目录一字一空/像AI写的」**：分别按 R12 加厚、R4 图文对等、R13 去空行、R10/R14 像素重嵌、R15 目录样式、R16 去 AI 腔处理，优先改 docx 而非全量重截

## 异常处理

- 项目无法运行：**优先使用已有截图缓存** 生成手册，或提示用户手动补图
- 源文件不足：取前部+后部真实源码拼接；禁止假代码
- Playwright 包缺失：只 `npm install playwright --no-save`，不顺便装浏览器
- launch 失败且为浏览器缺失：按策略只补装一次 chromium，优先系统 Chrome
- `__dirlock`：删除后重试 launch，勿并行 install
- 截图偏少：用详实文字步骤补齐；缺哪张补哪张，**不要删光重来**；同组已有截图若看起来一样，先删相似图或补做真实状态变化，不以重复图补数量
- 手册页数 <51 或用户要求51–60页：加概述/步骤/异常/读图说明实质内容或微调行距字号图宽（**复用现有图**，**禁止空行**），并 **R12 循环**直到51–60页
- 手册页数 >60：减少手册内重复引用、合并步骤（**不必重截**），循环直到≤60且不低于51
- 写入 docx 出现 EBUSY：改写 `操作手册-新版.docx` 并告知用户关闭 Word
- 端口被占用：换端口；确认页面属于当前项目再截图（防止截到其它项目）
- 用户反馈「只要改手册/改页数」：跳过截图阶段，直接基于缓存重生成 docx，并重新跑 R12
- 用户反馈「样式碎裂 / 一字一格」：按 R10 重生成手册，**禁止**因此全量重截
- 用户反馈「目录一字一空 / 目录像 AI」：按 R15 重写目录（左对齐+点线页码，去掉说明段），**不必重截**
- 用户反馈「流程截图少 / 只是展示」：补操作后状态图 + 按 R16 改写可操作步骤，可增量补截
- 用户反馈「同一组截图看起来一样 / 同组截图要有操作和变化」：执行 G5/R3/R14；按同一 `shotGroup` 重走真实操作，补筛选、选中、提交、审核、派发、回退、导出、锁定或归档等可见后果；对只有数字、时间、光标、轻微滚动或 toast 变化的图不写入手册，必要时减少该组截图数量，并重新做并排缩略图抽检
- 用户反馈「申请表格式要参考要求 / 不要随便改」：立即读取用户指定的 `文档参考`，以参考申请表为规范恢复字段和版式；不得继续沿用助手自定义的扩展格式。
- 用户反馈「申请表字数太少」：保持参考模板17项字段不变，只扩充已有字段中的真实业务内容，并重新验证 UTF-8、无 BOM、无空行、字段数量和申请表字数门禁（开发目的≤50、面向领域≤50、主要功能500–1300且单行、技术特点≤100、源程序量10000–50000纯数字）。
- 用户反馈「图太小」：提高嵌入宽度至约 5.2 英寸后重嵌 docx；若问题出在横向封面截图，则优先改封面为横向 section，而不是继续在竖版中放大。
- 用户反馈「截图拼在一起不好看」：禁止继续使用合成图；将每个流程态恢复为独立原始截图，并在相邻截图之间插入图示状态与读图提示后重新验页。
- 用户反馈「图不对/像侧边栏」：检查 transformation 是否误用 twip，按像素重嵌，**先改 docx**
- 用户反馈「不要有空行」：执行 R13，重生成申请表/代码/收紧手册空段
- 用户反馈「代码不够65页 / 多加代码 / 后端算法不够 / 页面大片留白」：执行 R19；补齐遗漏真实后端与领域算法源码，规范展开压缩长行，禁止重复/假代码/硬分页；Word/WPS循环实测到至少66页并运行验证脚本，再用 WPS 直接输出代码 PDF
